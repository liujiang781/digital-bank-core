# S2 与 S3 账户记账接口交接说明

版本：v1.0 执行版  
日期：2026 年 11 月 10 日  
适用范围：数字银行实验三，存款闭环优先，随后实现取款与本行转账。

本文固定 S2 与 S3 的开发接口、数据写入边界和联调标准。双方按本文实现，不再分别设计同一接口。仓库现有代码为工程骨架，本文中的业务端点和增量表是本轮开发交付内容，不能按已有可运行功能使用。

代码基线：`liujiang781/digital-bank-core`，提交 `f331eabb2d82d10a15fd23d809af096f0a55a5e4`。工程使用 JDK 21、Spring Boot 3.5.7；账户服务端口 8082，交易服务端口 8083，风控服务端口 8084。

## 1 双方负责的内容

| 工作 | S2 账户服务 | S3 交易与风控服务 |
|---|---|---|
| 对外账户接口 | 开户、账户列表/详情、余额、冻结/解冻、注销、限额、操作记录、资金流水查询 | 不重复实现 |
| 对外交易接口 | 不直接接收用户的存款、取款、转账申请 | 实现 `/api/v1/deposits`、`/withdrawals`、`/transfers`、`/transactions` |
| 用户权限 | 复核账户归属和操作权限；内部受理时复核原单身份与付款账户归属 | 对外接口先认证和校验对象权限，再认领幂等请求 |
| 交易受理幂等 | 对内部资金动作执行第二层幂等 | 按身份、业务类型、requestId 认领原单，并比较请求内容 |
| 风控 | 在最终受理事务内复核账户、余额及限额，防止快照过期 | 风控规则求值、风险事件记录和业务编排 |
| 渠道模拟 | 接收可信结果并完成本地资金处理 | 实现成功、失败、超时三种模拟结果，以及后续结果查询 |
| 资金处理 | 独占修改余额、占用金额、资金流水及资金状态 | 通过内部接口发命令，不直接改资金数据 |
| 验证 | 重复记账、资金原子性、余额不变式、冻结竞态 | 重复受理、风控拦截、渠道场景、超时恢复及对外结果 |

首轮共同目标是：用户发起一笔存款，经 S3 受理和渠道模拟后，S2 只增加一次余额、只生成一条存款流水，并将交易推进为成功。

## 2 数据与状态采用同一套口径

### 2.1 表与字段的写入归属

| 数据 | 写入方 | 约束 |
|---|---|---|
| `account` | S2 | S3 经接口读取，不直接更新 |
| `transaction_flow` | S2 | 仅追加真实资金变动；不修改、不删除 |
| `account_status_log` | S2 | 账户状态变更留痕 |
| `transaction` 的原单字段 | S3 | 写 `trade_no`、`identity_id`、`business_type`、`request_id`、`request_hash`、`account_id`、`amount`、`currency`、`created_at`；首次插入状态为 `ACCEPTED` |
| `transaction` 的推进字段 | S2 | 后续 `status`、`accepted_at`、`completed_at`、`channel_evidence_id`、`last_channel_result`、`last_checked_at`、`failure_reason` 由 S2 更新 |
| `transfer_order` | S3 | S2 读取本行转账的付款方、收款方、金额和币种；受理后不得更换交易要素 |
| `risk_rule`、`risk_event` | S3 | S2 只读必要规则和拒绝依据 |
| `account_reservation`、`account_command` | S2 | 本轮新增表，由 S2 提供增量 SQL，S4 统一执行 |
| `audit_log` | 各自服务 | 记录本服务的敏感操作、异常和矛盾结果 |

`transaction` 是有明确字段分工的共写表。S3 插入原单后，不自行把交易改成 `PROCESSING`、`UNKNOWN`、`SUCCESS`、`FAILED` 或 `REJECTED`，应调用 S2 的推进接口。

对外账户标识统一使用 `accountId`，对应 `account.account_id`。原表没有 `account_no`。`customerId` 是客户业务标识，`identityId` 是认证身份，不能混用。

### 2.2 状态与响应码

| 对象 | 固定取值 |
|---|---|
| 账户状态 | `ACTIVE`、`FROZEN`、`CLOSED` |
| 交易状态 | `ACCEPTED`、`PROCESSING`、`UNKNOWN`、`SUCCESS`、`RECOVERING`、`FAILED`、`REJECTED` |
| 渠道结果 | `SUCCESS`、`FAILED`、`UNKNOWN` |
| 逐笔预留状态 | `NONE`（查询表达，无记录）、`RESERVED`、`CONSUMED`、`RELEASED` |

旧稿中的 `NORMAL`、`RECEIVED`、`SUCCEEDED`、`PENDING` 不作为账户/交易状态写入数据库。公共响应外壳沿用现有 `ApiResponse`，其成功码仍是 `SUCCEEDED`，与业务终态 `SUCCESS` 分开理解。

```json
{
  "code": "SUCCEEDED",
  "message": "请求成功",
  "data": {
    "tradeNo": "TRD202611100001",
    "status": "SUCCESS",
    "reservationStatus": "NONE",
    "reasonCode": null
  },
  "traceId": "s2-s3-demo-001"
}
```

HTTP 200 和外壳 `SUCCEEDED` 仅说明内部命令已得到处理。S3 必须检查 `data.status`，不能据此直接向用户显示存款成功。

### 2.3 金额、时间与请求号

- 接口金额使用两位小数字符串，例如 `"100.00"`；Java 使用 `BigDecimal`，数据库使用 `DECIMAL(18,2)`。拒绝负数、零金额、超过两位小数及超出字段范围的金额。
- 币种固定为 `CNY`。所有修改余额的命令都要与原单的金额和币种一致。
- 时间使用东八区 ISO-8601，例如 `2026-11-10T15:30:00+08:00`；入库按上海时区转换。
- 用户对外 POST 的 `requestId` 放 JSON 请求体，使用 UUID；同时提供 `X-Request-Id` 时，两者必须相同，否则返回 400。
- 服务间资金命令按 `tradeNo + 动作` 幂等，不另生成用户交易请求号；同一动作重试沿用原 `tradeNo`。
- `X-Trace-Id` 全程透传；一次重试可以有新的 traceId，但不能因此生成新的交易号。

## 3 内部调用与认证

S3 使用环境变量 `ACCOUNT_SERVICE_URL` 定位 S2，默认 `http://localhost:8082`。所有内部调用直接访问账户服务，不经过网关。

两个服务使用同一份环境配置 `ACCOUNT_INTERNAL_TOKEN`。每次请求携带：

```http
Content-Type: application/json
X-Internal-Token: <ACCOUNT_INTERNAL_TOKEN 的实际值>
X-Trace-Id: s2-s3-demo-001
```

令牌由运行环境生成至少 32 字节的随机值，不写进代码、示例数据或提交记录。S2 配置为空时关闭内部接口；缺少或错误令牌返回 401 `UNAUTHENTICATED`。`/internal/v1/**` 不由网关路由，但 S2 仍须检查令牌。

本轮渠道是 S3 内部的模拟渠道。S3 按 `tradeNo` 保存稳定的渠道请求标识与结果，确认结果来自自身模拟渠道后再通知 S2；不开放匿名渠道回调。S2 校验内部令牌，并复核回执与已登记原单的交易号、账户、金额、币种。客户端提交的“成功”字段不能直接作为入账依据。

S3 提供自己的增量表 `mock_channel_deposit`，至少保存 `trade_no`（主键）、`channel_request_id`（唯一）、`account_id`、`amount`、`currency`、`result`、`evidence_id`、`observed_at`、`created_at`、`updated_at`。另保存 `reconcile_attempts`（整数，初始 0）、`next_check_at`（可空时间）、`manual_review_required`（布尔，初始 false），用于持久化有界核对进度。字段长度与接口一致，金额为 DECIMAL(18,2)，result 仅允许 SUCCESS/FAILED/UNKNOWN；account_id 和 trade_no 分别关联原账户与原单。channelRequestId 固定为 `CHD` 加 tradeNo，避免重试重新生成渠道请求。明确结果只能由 UNKNOWN 收敛为 SUCCESS 或 FAILED，终态结果不能翻转。此表由 S3 写入和提供迁移脚本，S4 执行；S2 不写该表。

业务服务不信任客户端自行设置的 `X-Customer-Id` 或 `X-Identity-Id`。S1 的认证上下文接入后，S3 从服务器认证身份取得 `identityId`；内部请求中的身份由 S3 负责传递，S2 负责与数据库账户归属复核。

## 4 存款按以下顺序调用

1. S3 认证用户，校验请求格式及账户权限，按三元组认领交易原单，初始为 `ACCEPTED`。重复请求返回原单的当前状态。
2. S3 从 S2 获取账户快照，调用风控。风控拒绝时记录风险事件，再调用 S2 的拒绝接口结束原单，不调用渠道。
3. 风控通过后，S3 调用 S2 的 `deposit-acceptances`。S2 锁定交易和账户，复核状态、身份、金额及限额，写入 `accepted_at`，推进为 `PROCESSING`。
4. 只有账户侧受理成功，S3 才调用模拟渠道。
5. S3 将渠道结果发送给 S2 的 `deposit-results`：明确成功才入账，明确失败才失败，超时或未知保持 `UNKNOWN`。
6. S3 根据 S2 返回或查询得到的当前状态向用户反馈。待确认交易继续沿原 `tradeNo` 查询和核对。

**冻结与受理采用同一账户行锁串行化。** 冻结先提交，新存款受理被拒绝；受理先提交，后续冻结不阻止该笔已受理存款确认。`ACCEPTED` 只是 S3 已登记原单，不代表已通过账户状态检查。不能只比较精度为秒的时间戳来判断先后。

## 5 首轮必须提供的接口

以下是 S2 的交付清单。标记“新增”的接口用于补齐原设计中未明确的受理、未知结果和查询步骤，名称按本表固定。

| 方法与路径 | 用途 | 来源 |
|---|---|---|
| `POST /internal/v1/accounts/snapshots` | 返回付款/存款账户的授权快照，供 S3 风控使用 | 新增 |
| `POST /internal/v1/postings/deposit-acceptances` | 账户侧原子受理存款 | 新增 |
| `POST /internal/v1/postings/deposit-results` | 处理成功、失败、未知三类渠道结果 | 新增，S3 首选此入口 |
| `GET /internal/v1/postings/{tradeNo}` | 查询资金处理当前状态，供超时恢复使用 | 新增 |
| `POST /internal/v1/postings/failures` | 记录受理前拒绝或受理后明确失败 | 原有端点，字段在本文固定 |
| `POST /internal/v1/postings/deposit-completions` | 仅接收 `result=SUCCESS`，行为同 `deposit-results` 成功分支 | 原有端点，保留兼容 |

### 5.1 获取账户快照

```json
{
  "identityId": "identity-demo-001",
  "businessType": "DEPOSIT",
  "accountId": "ACC_S2_001",
  "payerAccountId": null,
  "payeeAccountId": null
}
```

存款使用 `accountId`；取款使用 `payerAccountId`；本行转账同时提供 `payerAccountId` 和 `payeeAccountId`。S2 校验存款/付款账户属于该身份。本行收款账户只返回标识、币种和状态，不向付款方暴露收款方余额。

存款/付款账户的 `data.account` 返回：`accountId`、`currency`、`status`、`bookBalance`、`reservedAmount`、`availableBalance`、`effectiveSingleLimit`、`effectiveDailyLimit`、`dailyUsedAmount`、`ruleVersion`。转账另返回 `data.payee` 的 `accountId/currency/status`。

快照只供风控预判；最终受理仍须在 S2 的数据库事务中再次复核，不能拿快照代替加锁后的判断。

限额默认值为存款单笔 `50000.00`、出账单笔 `10000.00`、日累计出账 `50000.00`。启用的 `LIMIT_POLICY` 规则优先，按 `rule_version` 降序、`id` 降序取第一条；个人出账限额与系统限额取较小值。日额度按首次账户侧受理时间 `accepted_at` 的上海自然日归属：当日成功出账金额，加上当日 `status=RESERVED` 的预留金额。`CONSUMED` 已计入成功出账，不再次累加；`RELEASED` 不计入。跨日完成仍归原受理日，重复调用不改变归属日期。

### 5.2 账户侧受理存款

```http
POST /internal/v1/postings/deposit-acceptances
```

```json
{
  "tradeNo": "TRD202611100001",
  "accountId": "ACC_S2_001",
  "amount": "100.00",
  "currency": "CNY"
}
```

S2 要求原单已存在、业务类型为 `DEPOSIT`，且身份、账户、金额、币种匹配。通过后同事务写 `PROCESSING` 与 `accepted_at`，余额和资金流水保持不变。重复相同受理返回当前状态，不重复修改受理时间。

账户状态或限额等业务复核拒绝时，S2 持久化 `REJECTED` 与原因，再正常返回 `PostingOutcome`；`reasonCode` 使用既有错误码，例如 `ACCOUNT_STATUS_INVALID`。S3 将其映射成相应的对外 422 错误。该拒绝结果不能因随后抛出异常而被事务回滚。

### 5.3 上报渠道结果

```http
POST /internal/v1/postings/deposit-results
```

```json
{
  "tradeNo": "TRD202611100001",
  "accountId": "ACC_S2_001",
  "amount": "100.00",
  "currency": "CNY",
  "result": "SUCCESS",
  "channelRequestId": "CHDTRD202611100001",
  "evidenceId": "EVD202611100001",
  "observedAt": "2026-11-10T15:30:00+08:00",
  "reasonCode": null
}
```

| 字段 | 规则 |
|---|---|
| `tradeNo/accountId/amount/currency` | 必填，与原单逐项一致；不从回执创建新交易 |
| `result` | 必填，只接受 `SUCCESS/FAILED/UNKNOWN` |
| `channelRequestId` | 必填，固定为 `CHD` 加 tradeNo，最长 64 字符；S2 按此公式校验，不允许重试时更换 |
| `evidenceId` | 明确成功/失败时必填，最长 64 字符；UNKNOWN 可为空 |
| `observedAt` | 必填，S3 获取本次结果的东八区时间 |
| `reasonCode` | FAILED 必填，最长 64 字符；例如 `CHANNEL_DECLINED`；UNKNOWN 可填 `CHANNEL_TIMEOUT` |

S2 根据数据库中自己的受理记录判断是否能处理回执，不接受对尚未通过账户侧受理的原单直接入账。

| 结果 | S2 原子处理 | 交易状态 |
|---|---|---|
| SUCCESS | 增加 B、追加一条 `DEPOSIT_IN/CREDIT` 流水、记录凭证及完成时间 | `SUCCESS` |
| FAILED | 记录失败依据和完成时间；不加钱，不生成资金流水 | `FAILED` |
| UNKNOWN | 更新最近核对信息；不改余额、不写资金流水、不设置完成时间 | `UNKNOWN` |

同一成功结果重复上报只返回原状态。成功后又收到失败、失败后又收到成功等矛盾稳定结果，保留已有终态，写审计记录并返回 409 `REQUEST_CONFLICT`，不得反向改余额。终态后收到延迟 UNKNOWN，直接返回已有终态。

数据库映射固定为：`last_channel_result=result`、`last_checked_at=observedAt`、`channel_evidence_id=evidenceId`；UNKNOWN 不清除已有凭证。`transaction.failure_reason` 保存机器可读的 `reasonCode`，详细说明写入 `audit_log.reason`，查询时由 failure_reason 还原 Outcome.reasonCode。终态后的延迟 UNKNOWN 不覆盖终态的状态、凭证或完成信息。

### 5.4 查询资金结果

```http
GET /internal/v1/postings/TRD202611100001
```

所有资金接口的 `data` 统一为以下 `PostingOutcome`：

| 字段 | 类型 | 说明 |
|---|---|---|
| `tradeNo` | string | 原交易号 |
| `status` | string | 当前交易状态，使用数据库字面量 |
| `reservationStatus` | string | `NONE/RESERVED/CONSUMED/RELEASED` |
| `reasonCode` | string 或 null | 拒绝/失败的原因；正常处理中和成功可为空 |

结果查询从主库读取。S3 对外的交易查询还要先校验用户与原单的访问权限，不能把内部查询接口直接暴露给前端。

### 5.5 记录拒绝或明确失败

```http
POST /internal/v1/postings/failures
```

```json
{
  "tradeNo": "TRD202611100001",
  "decision": "REJECTED",
  "reasonCode": "SINGLE_LIMIT_EXCEEDED",
  "evidenceType": "RISK_EVENT",
  "evidenceId": "RSKEVT202611100001"
}
```

- `decision=REJECTED` 仅适用于尚未账户侧受理、没有预留和资金流水的 `ACCEPTED` 原单。风险拒绝要求 `evidenceType=RISK_EVENT`，且风险事件属于同一原单。S2 持久化拒绝状态，S3 不再调用渠道。
- `decision=FAILED` 仅用于取款及本行转账已经确定的本地业务失败，`evidenceType` 固定为 `LOCAL_FAILURE`，`evidenceId` 与 `reasonCode` 必填。S2 释放该交易自己的预留并推进失败，全部在本地事务内完成。`LOCAL_FAILURE` 不包括网络超时、响应丢失或渠道结果未知，不得据此终结未决交易。
- DEPOSIT 的成功、失败和未知结果统一通过 `deposit-results`；`deposit-completions` 仅保留成功分支兼容入口。UNKNOWN 不调用 failures；本轮不在 failures 上接入跨行渠道失败。
- 本接口返回 `PostingOutcome`，终态不得重开。失败恢复重试沿用相同原单和失败依据。

## 6 取款与本行转账的后续接口

先完成第 5 节存款闭环，再按本节扩展。端点名称和数据约定已固定。

| 方法与路径 | 必填 JSON 字段 | S2 的处理 |
|---|---|---|
| `POST /internal/v1/postings/reserve` | `tradeNo,payerAccountId,amount,currency`；本行转账还需 `payeeAccountId` | 检查原单、归属、账户状态、可用余额、限额；R 增加，建立该交易预留，置 PROCESSING |
| `POST /internal/v1/postings/withdrawal-completions` | `tradeNo,payerAccountId,amount,currency` | 消耗原预留，B/R 同减，追加 WITHDRAW_OUT/DEBIT，置 SUCCESS；本轮新增取款提交端点 |
| `POST /internal/v1/postings/internal-transfers` | `tradeNo,payerAccountId,payeeAccountId,amount,currency` | 消耗原预留，付款 B/R 同减、收款 B 增，追加双方流水，置 SUCCESS |
| `POST /internal/v1/postings/releases` | `tradeNo,payerAccountId,amount,currency,reasonCode,evidenceType,evidenceId` | 根据明确失败依据释放该交易预留并置 FAILED；与 failures 的出账失败分支相同 |

取款固定调用顺序：S3 认领原单 → 风控 → S2 reserve → S2 withdrawal-completions。  
本行转账固定调用顺序：S3 认领原单并写 transfer_order → 风控 → S2 reserve → S2 internal-transfers。

S2 不接受没有原预留记录的直接扣款或本行转账提交。本行转账的收款账户必须与 `transfer_order.payee_account_id` 一致，不能凭重试请求更换收款方。冻结后的新付款或新转入在 reserve 阶段拒绝；已经成功预留并受理的业务允许继续确认或恢复。

本行转账受理和提交均按 `accountId` 字典序锁定双方账户，统一采用“锁交易行 → 按固定顺序锁账户”的顺序。双方余额、占用、双方流水和成功状态在同一数据库事务中提交，任一步失败则全部回滚。

所有成功出账与释放接口都要二次检查原单类型、账户、金额、币种；相同命令重复调用返回当前结果，不重复扣款、不重复释放其他交易的占用。

releases 的 `evidenceType` 同样固定为 `LOCAL_FAILURE`，不得把超时作为释放依据。本轮存款、取款和本行转账的失败处理由同库事务整体完成；若事务失败，原状态和资金一起回滚，S3 查询后沿原单重试。已存在的 `RECOVERING` 原单可以携原明确失败依据重试释放，只有恢复完整提交后才置 FAILED，不因一次 HTTP 返回而假定恢复完成。

## 7 两层幂等与数据库增量

### 7.1 S3 负责请求幂等

幂等键固定为 `(identityId,businessType,requestId)`，使用现有唯一索引兜底。先完成认证和对象权限检查，再认领原单。

同键同内容返回原 `tradeNo` 和当前状态；同键不同内容返回 409 `REQUEST_CONFLICT`。`SUCCESS/FAILED/REJECTED` 不重新执行；用户确实发起另一笔业务时才使用新的 requestId。

只有成功认领新原单的一方启动首次编排。重复请求命中已有原单时只返回当前结果，不再次启动渠道调用；未完成业务由按原 tradeNo 执行的查询/核对流程继续处理。模拟渠道也以 tradeNo 唯一，不能因 HTTP 重试创建第二笔渠道入金。

S3 进程启动后以及每 10 秒扫描一次非终态原单，沿原 tradeNo 从未完成步骤恢复。ACCEPTED 原单继续风控和账户侧受理；PROCESSING 原单先查 S2 资金结果，再查询或复用唯一的模拟渠道记录。渠道记录尚未创建时，以固定的 `CHD + tradeNo` 原子创建或读取，不生成第二个逻辑渠道请求；已有记录只查询和复用。UNKNOWN 原单只在 next_check_at 到期且 manual_review_required=false 时自动核对，扫描和进程重启都不重置已持久化次数。恢复任务按 tradeNo 串行处理，不能因首次认领进程退出而使原单永久停留。

请求指纹固定为 SHA-256，输入是下列顺序的紧凑 JSON 数组的 UTF-8 字节：

```text
[businessType, accountId, payerAccountId, payeeAccountId, amount, currency, purpose]
```

不用的账户字段和未提供的用途统一为空字符串；amount 规范化为两位小数，currency 固定 CNY，purpose 去除首尾空白。存款示例：

```json
["DEPOSIT","ACC_S2_001","","","100.00","CNY",""]
```

取款和本行转账的 `accountId` 与 `payerAccountId` 均填付款账户。requestId 和 traceId 不进入内容指纹。跨行扩展时另立契约版本，本轮不加入外部银行字段。

### 7.2 S2 负责资金动作幂等

S2 锁定原单后，结合交易状态、逐笔预留记录和流水唯一键判断动作是否已经生效。`transaction_flow` 沿用唯一键 `(trade_no,account_id,entry_role)`。

新增 `account_reservation` 至少包含：`trade_no`（主键）、`account_id`、`amount`、`status`、`created_at`、`updated_at`。币种与本轮系统均固定 CNY，命令仍须与原单核对币种。预留记录与账户 R 同事务创建；提交或释放只能消耗这一条记录。

新增 `account_command` 保存开户、冻结/解冻等账户操作的请求幂等结果，不把 FREEZE、UNFREEZE 等值强塞进 `transaction.business_type`。该表由 S2 自己使用，S3 不写入。

S2 和 S3 各自提供独立增量 SQL。S4 先执行实验二基础 schema，再执行 S2 的账户增量和 S3 的模拟渠道增量，配置各服务权限。已有数据环境不重跑带 DROP TABLE 的基础脚本。S3 不创建另一份预留表，也不直接写 S2 两张增量表。

余额始终满足：`A = B - R`、`B >= 0`、`0 <= R <= B`。只占用或释放金额时，不生成资金流水。

## 8 超时、重试和异常按统一规则处理

| 情况 | S3 固定处理方式 | S2 保证 |
|---|---|---|
| 内部请求连接超时/响应丢失 | 先 GET 同一 tradeNo 的资金结果，再决定是否重发同一命令；不创建新原单 | 同一命令重复执行不会重复产生资金效果 |
| 渠道调用超时 | 上报 UNKNOWN，向用户展示待确认，按原 channelRequestId 查询渠道 | 不误判失败，不加钱，不释放占用 |
| 同键异内容或回执关联不符 | 返回/展示冲突，保留原单 | 返回 409，余额不变 |
| S2 校验后正常拒绝 | 读取 Outcome 的 REJECTED 和 reasonCode，对外映射相应业务错误 | 拒绝状态已持久化，不产生流水 |
| S2 数据库或未预期异常 | 返回可查询提示，查询原单后再重试 | 本地事务整体回滚，不能出现单边资金变化 |
| 终态后的矛盾明确回执 | 停止自动推进，记录异常并转运营核对 | 保留终态，不重复入账或反向改余额 |

S3 内部 HTTP 连接超时设为 2 秒、响应超时设为 5 秒。可重试命令最多自动重试 3 次，间隔 1、2、4 秒；每次重试前先查询资金结果，参数保持不变。400/401/403/409 不自动重试；持久化业务拒绝不重试。

UNKNOWN 交易每 10 秒查询一次模拟渠道，每次持久增加 reconcile_attempts，自动核对最多 6 次。仍未知则保留待确认，置 manual_review_required=true、next_check_at=null，停止自动核对；供用户后续主动查询或运营手动核对。主动查询/手动核对只沿原单、原渠道请求标识查询一次，不重启一轮自动任务。不得因次数用尽而改成 FAILED，也不得重新发起一笔新的渠道入金。

本轮所有资金判断和结果确认读主库。跨 HTTP 调用不放进一个长数据库事务，也不把 `@Transactional` 当成跨服务事务。

## 9 联调按此清单验收

联调数据由 S4 初始化两个不同客户及账户：`ACC_S2_001`、`ACC_S2_002`，身份与客户记录真实关联。S3 用真实初始化身份发起业务，不在测试里混用 customerId 与 identityId。

| 编号 | 场景 | 验收结果 | 主验证方 |
|---|---|---|---|
| T01 | 正常存款 100.00 | B 增加 100.00；一条 DEPOSIT_IN；原单 SUCCESS | S2 + S3 |
| T02 | 同 requestId 同内容重复提交 | 同一个 tradeNo，余额与流水只变化一次 | S3 |
| T03 | 同 requestId 不同金额 | 409；不产生第二笔交易或资金效果 | S3 |
| T04 | 同成功回执重复及并发上报 | 只入账一次，只存在一条对应流水 | S2 |
| T05 | 已冻结账户发起新存款 | 账户侧拒绝；渠道未调用；余额不变 | S2 + S3 |
| T06 | 先账户侧受理，再冻结，再成功回执 | 原业务可以完成，仍只入账一次 | S2 + S3 |
| T07 | 渠道明确失败 | FAILED；B/R 不增加；无存款流水 | S3 |
| T08 | 渠道先未知，后成功 | UNKNOWN 时余额不变；确认后只入账一次 | S2 + S3 |
| T09 | 内部成功后响应丢失，再查询/重试 | 查询 SUCCESS；重试无第二次资金效果 | S2 + S3 |
| T10 | 回执交易号/账户/金额/币种不匹配 | 拒绝处理，原资金与状态不被篡改 | S2 |
| T11 | 取款预留、提交与重复提交 | R 仅增加一次；提交 B/R 同减；一条取款流水 | S2 |
| T12 | 明确失败后重复释放 | 仅释放原交易一次，不影响其他预留 | S2 |
| T13 | 本行转账成功 | 付款与收款金额相等，双方流水同 tradeNo | S2 + S3 |
| T14 | 转账中途写入异常 | 双方余额、预留、流水、成功状态全部回滚 | S2 |
| T15 | 风控拒绝 | 有 risk_event；交易 REJECTED；无资金流水 | S3 |
| T16 | 内部令牌错误或越权访问 | 401/403/404 按契约返回；不产生资金变化 | S2 + S3 |

S2 提供事务及余额 SQL 核验记录；S3 提供请求、渠道场景和状态查询记录。两个模块都完成后，再与 S5 进行真实前端联调。未运行的测试不填写“通过”。

## 10 开发交付顺序

1. S2 交付快照、存款受理确认、渠道结果处理、资金结果查询、增量 SQL，以及请求/响应示例。
2. S3 交付存款入口、三元组幂等、风控调用、三种渠道结果、查询与有界重试。
3. 共同执行 T01—T10、T15—T16，先完成存款闭环。
4. S2 交付 reserve、取款提交、本行转账与失败释放；S3 接上对应编排，执行 T11—T14。

S2 的交付边界到“可靠执行一次资金动作并返回当前状态”；S3 的交付边界到“可靠受理和编排一次业务，并向用户解释当前结果”。双方以同一个 tradeNo 串联日志、交易、预留和资金流水。
