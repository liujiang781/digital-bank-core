# S2 账户与资金记账实现说明

本次交付将实验二账户域设计接入 Java 21 / Spring Boot 3.5.7 骨架，实现账户生命周期及 S3 调用的资金执行边界。S2 负责余额、逐笔预留、实际资金流水与资金状态在本地事务内一致；S3 负责外部交易受理、风控编排和模拟渠道。

代码基线为 `f331eabb2d82d10a15fd23d809af096f0a55a5e4`。业务接口以 [S2/S3 交接执行版](S2-S3接口交接说明.md) 为准。运行步骤、环境变量、接口列表见 [账户服务 README](../README.md)。

本轮按组长的目录分工交付，全部 S2 改动集中在 `backend/account-service/`。模块所需数据库增量作为交接材料提供，由 S4 统一纳入 `deploy` 执行；父工程、公共模块和其他成员目录沿用原骨架。

## 1 实现内容与交付边界

| 内容 | 实现要点 |
|---|---|
| 开户 | 校验实名客户；锁定客户行后核对三个未注销账户上限；初始 B/R/A 为零 |
| 查询 | 本人或授权范围内的账户、余额、操作记录和实际资金流水；金额按两位小数字符串输出 |
| 冻结与解冻 | 与资金受理共用账户行锁；每项限制留痕；解冻要求有权限的运营人员提供覆盖全部有效限制的依据 |
| 个人限额与注销 | 个人限额不超过系统上限；注销要求零余额、零占用、无未决原单和有效冻结限制 |
| 存款 | 账户侧受理确认、渠道成功/失败/未知处理、按原交易查询；成功一次性写余额、流水与状态 |
| 出账 | 逐笔预留、取款提交、本行转账、明确失败释放；固定顺序锁账户，避免单边提交 |
| 权限与输入 | 服务器 Principal 适配；内部服务令牌；对象归属复核；金额精度、请求号与关联字段校验 |

S2 不实现用户登录、模拟渠道、对外存款表单或风控服务。其验证与联调由相应负责人完成，S2 提供账户与资金端点。

## 2 数据写入和增量脚本

沿用实验二 `payment_db`，先执行基础 schema，再执行 `backend/account-service/src/main/resources/db/s2-incremental.sql`。应用不会自动重建业务数据库。

| 表 | S2 的写入范围 |
|---|---|
| `account` | 生命周期、余额、预留、个人限额与版本 |
| `transaction_flow` | 只追加实际资金变动；唯一键 `(trade_no, account_id, entry_role)` |
| `account_status_log`、`audit_log` | 账户状态、操作依据和异常留痕 |
| `transaction` | 推进 `status/accepted_at/completed_at/channel_evidence_id/last_channel_result/last_checked_at/failure_reason` |
| 新增 `account_reservation` | 以 trade_no 唯一记录该笔出账的 RESERVED/CONSUMED/RELEASED |
| 新增 `account_command` | 账户生命周期请求的身份、动作、请求号、指纹与结果 |

S3 插入金融原单及转账单，不直接改资金字段。S3 自己提供模拟渠道持久化表和增量 SQL。S4 负责在同一主库执行各增量脚本及分配访问权限。

## 3 一致性与幂等

余额满足 `A=B−R`、`B≥0`、`0≤R≤B`。预留和释放只改变 R，不产生实际资金流水。

S3 对客户端请求按 `(identityId,businessType,requestId)` 认领原单并比较指纹；S2 对每个资金动作按原 tradeNo 加锁，复核账户、金额、币种和类型，再结合状态、逐笔预留及流水唯一键判断是否已生效。同一成功回执或提交命令重试不会再次产生资金效果。

存款账户侧受理与冻结采用同一账户行锁串行化。冻结先提交则新受理拒绝；受理先提交则写入 accepted_at，后续冻结仍允许该笔原业务完成。交易表的初始 ACCEPTED 仅代表登记，不代替账户侧复核。

存款成功时，增加 B、写 DEPOSIT_IN 流水、记录凭证及推进 SUCCESS 在同一数据库事务提交。UNKNOWN 不改余额、不写流水、不设置完成时间；明确失败才终结。终态之后的矛盾稳定回执保留原状态，记录审计并返回冲突。

出账受理建立逐笔预留；取款提交消耗预留并使 B/R 同减；本行转账按账户标识固定顺序锁定双方，付款 B/R 同减、收款 B 增、双方流水及 SUCCESS 一起提交。任一步数据库写入失败则该事务全部回滚。失败释放只消耗原 tradeNo 的预留，不影响其他交易。

日额度按首次账户侧受理时间 accepted_at 的上海自然日归属，计算同日成功出账和同日 RESERVED 金额。CONSUMED 不重复累加，RELEASED 不计入；跨日完成保留原受理日。

资金写事务采用 READ COMMITTED，锁定交易及账户后复核额度，避免缺失预留行上的范围锁与旧快照干扰；查询快照采用 REPEATABLE READ。连接会话固定为 +08:00，DATETIME 以 LocalDateTime 读写。测试进程使用 UTC 默认时区，验证跨时区运行仍按上海自然日计算额度。

RECOVERING 只允许携原失败原因与原凭证恢复释放，迟到成功不能消耗该预留。失败原因使用规范大写机器码，超时、未知或响应丢失不能冒充明确失败。矛盾终态的 409 在资金变更前产生，专门保留冲突审计，其他数据库异常仍整体回滚。

## 4 认证适配与协作接口

对外接口读取服务器 Servlet Principal。S1 可注入本模块 Actor，提供 identityId、customerId、岗位与账户授权范围；普通 Principal 只映射客户身份。任意客户端身份头不会获得权限。S1 的认证过滤器和真实登录尚需联调，当前模块不会通过自定义请求头替代正式认证。

S3 内部调用直接访问 8082，携带双方相同的 ACCOUNT_INTERNAL_TOKEN 和 X-Trace-Id。令牌为空时拒绝内部访问。渠道结果由 S3 的稳定模拟渠道提供，channelRequestId 固定为 CHD 加 tradeNo；S2 复核原单关联后处理。

接口外壳沿用 `ApiResponse` 的 `SUCCEEDED`。这是命令处理成功标记，资金业务状态另见 data.status；REJECTED 不等于入账成功。S3 必须依据当前业务状态向用户反馈，内部超时后沿原单查询或重试。

## 6 联调核验方式

1. S4 准备两个正常实名客户及真实关联的演示账户。
2. S3 插入一个有唯一请求键的原单，依次调用账户侧受理和模拟渠道结果。
3. 由 S2 查询 B/R/A、逐笔预留、资金流水和 transaction.status；使用相同命令重复及并发调用，确认资金只生效一次。
4. 先冻结再受理应 REJECTED；先受理再冻结仍允许确认原业务。
5. 模拟 UNKNOWN 后查询原渠道结果，再发送稳定成功；在 UNKNOWN 期间不增加余额。
6. 转账或取款中制造数据库写入失败，比较调用前后余额、预留、流水和交易状态，确认无部分提交。
7. S1 接入真实 Principal、S3 完成真实编排后，再由 S5 执行前端完整业务流程并保存截图及调用记录。
