# 实验一需求补齐 S2 与 S3 联调交接

这次按 `main@49e511f` 完成了取款渠道、风控解除结论和运营查询的后端接线。S2 的限额校验与账户流水也在同一补丁里。请一起审阅并合并账户、交易和风控三个服务的改动。

## 取款回执与资金处理

`POST /api/v1/withdrawals` 的对外请求保持原样。交易服务先完成幂等认领、风控校验和账户预留，再复用模拟渠道，以 `tradeNo` 为唯一订单标识。渠道请求号固定为 `CHD` 加 `tradeNo`。交易服务把回执发给账户服务的 `POST /internal/v1/postings/withdrawal-results`，沿用账户服务内部令牌。

```json
{
  "tradeNo": "TRD202611190001",
  "payerAccountId": "ACC_S2_001",
  "amount": "100.00",
  "currency": "CNY",
  "result": "SUCCESS",
  "channelRequestId": "CHDTRD202611190001",
  "evidenceId": "EVDTRD202611190001",
  "observedAt": "2026-11-19T19:30:00+08:00",
  "reasonCode": null
}
```

| 回执结果 | 账户服务处理 | 查询状态 |
|---|---|---|
| `SUCCESS`，带明确证据编号 | 校验原单，再扣账、消费预留和追加一条 `WITHDRAW_OUT` 流水 | 本地记账完成后为 `SUCCESS` |
| `FAILED`，带明确证据编号及失败原因 | 先保存明确失败回执，再释放资金和原受理日额度 | 释放前为 `RECOVERING`，释放完成为 `FAILED` |
| `UNKNOWN`，无明确证据编号 | 保留预留和原受理日额度 | `UNKNOWN`，页面显示待确认 |

同一明确回执可以按原单重放。相反的明确结果会被拒绝并留审计。旧的 `withdrawal-completions` 入口只允许完成已有成功证据的取款。恢复扫描和运营人工核对接入了同一回执入口，有明确失败依据的恢复重试沿用原单和原证据。旧版已登记本地失败依据的恢复单继续走原恢复路径。

## 风控解除结论

1. 风控在授权范围内查询 `GET /api/v1/accounts/{accountId}`。冻结列表每条都有 `restrictionId`、`source` 和 `releaseApproved`。风控来源为 `RISK`，运营来源为 `OPERATIONS`。
2. 风控完成复核后调用 `POST /api/v1/risk/accounts/{accountId}/restrictions/{restrictionId}/release-approval`，请求体为 `{"basis":"复核确认风险已解除"}`。必须是授权范围内的风控人员，请求中的账户和编号必须匹配一条有效风控冻结。依据去除首尾空白后最多 200 字。
3. 风控服务向 `risk_freeze_release` 写入一条肯定的解除结论，保存原冻结编号、风控人员、依据和时间。相同编号和相同依据重放返回原结论，改用另一份依据返回 409。账户服务按原冻结编号读取结论。
4. 授权运营调用原 `POST /api/v1/accounts/{accountId}/unfreeze`，提交 `reason`、`releaseEvidence`、全部当前有效的 `resolvedRestrictionIds` 和 `requestId`。每一条风控限制都须已有解除结论，成功后账户变为 `ACTIVE` 并记录操作。审批完成到运营执行之间，账户保持冻结。

## 运营查询与前端接入

- `GET /api/v1/transactions/{tradeNo}` 返回已提交的状态快照，并带 `accountId`。普通客户查询本人交易。运营和风控按交易所属账户授权，调用详情、列表或回单时填写 `reason`，去除首尾空白后最多 255 字。核对和恢复使用 PR #44 的 POST 入口。
- `GET /api/v1/accounts/{accountId}/fund-entries` 接受 `tradeNo` 过滤。S5 可以用详情返回的 `accountId` 和 `tradeNo` 打开对应流水。运营和风控填写 `reason`，最多 200 字，账户服务审计账户、交易号和查询原因。客户仍按本人账户查流水。
- 限额页面提交 `POST /api/v1/accounts/{accountId}/limits`，字段为 `personalSingleLimit`、`personalDailyLimit` 和 `requestId`。金额使用两位小数字符串。新日限额低于当天已成功与仍占用的合计时，后端返回 400，错误消息包含当天已用金额。冻结、解冻、注销和操作记录页面继续调用现有账户接口。

## 数据库上线与联调

已有库在启动三个新版本服务前先执行 [增量 SQL](../../../deploy/sql/s2-requirement-gaps-incremental.sql)，再补齐 [部署说明](../../../deploy/README.md#4-服务账号与授权) 中相关表的授权。全新库通过 `deploy/sql/schema.sql` 初始化完整表结构。账户服务只读解除结论，风控服务写入结论。

联调时跑一次取款成功、明确失败、待确认后核对，并检查出账流水与预留。限额验证采用 8,000 元已成功＋2,000 元仍占用，9,999.99 元应拒绝、10,000 元可生效。冻结后分别验证缺少风控结论和已核验全部限制的解冻结果。运营查询验证缺少原因、超出账户范围和合法查询的响应，核查审计记录。

本地全后端回归 262 项通过。独立 MySQL 8.4.13 经网关联调通过 19 项检查，覆盖已有库重复迁移、降额与新取款并发、取款三态、明确失败后释放重试、交易服务重启后自动核对、风控与运营分角色解冻，以及运营查询原因和审计。
