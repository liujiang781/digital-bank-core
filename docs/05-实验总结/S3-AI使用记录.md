## 三、典型 Prompt 原文

### Prompt 1

```
我负责实验四的 S3 部分（存款、幂等与风控测试）。帮我根据《实验四分工表》和《实验四-S2与S3交接》，
从 RiskCheckService.check() 或 IdempotencyService.claim() 里选一个方法做基本路径分析：
画控制流图、算 V(G)、推导独立路径并给每条路径的输入。输出用中文。
```

**输出摘要**：给出了 `RiskCheckService.check()` 的节点/边划分、V(G)=9、9 条独立路径与对应输入建议。
**评价**：骨架可用；但初稿把"金额非法抛异常"当成了显式判定节点，人工改回"调用节点 + 边界用例"，并补了"存款不校验日累计"的路径。

### Prompt 2

```
给 DepositService/DepositController 补一个币种校验，非 CNY 抛 INVALID_ARGUMENT，和取款/转账保持一致。
同时写 DepositApiTest，用 MockMvc + @MockitoBean 打 AccountClient/RiskClient 桩，覆盖成功、重放、冲突、
非 CNY、未认证、越权、风险拒绝、渠道 UNKNOWN。用 Spring Boot 3.5 的写法。
```

**输出摘要**：给出修改方案与测试类骨架，并提示 Spring Boot 3.5 用 `@MockitoBean`。
**评价**：采用；人工补充了"`when(...)` 覆盖既有桩会触发旧桩 NPE、改用 `doAnswer(...)`"这一 Mockito 细节，以及账户不可用等失败路径。

## 四、AI 生成后被否决的内容及原因

| 内容 | 否决原因 |
|---|---|
| 用真实 MySQL 起临时实例时把数据目录建到非项目盘 | 用户明确"项目文件都放软工AI、不碰其他盘"；最终使用本机已装的 MySQL + S4 的 deploy 包 |
| 把取款/转账的完整功能链路（余额不足、冻结转账）填"通过" | 这些依赖 S2 记账侧，S3 单侧无法验证，按"未执行、注明原因"处理，不虚报 |

## 五、效率影响与体会

本次实验四 AI 在"读懂分工表和交接文档 → 生成测试骨架 → 跑测试看报告 → 搭真实环境跑联调"这条链路上帮助最大：基本路径法的节点划分、等价类表格、MockMvc 测试样板、MySQL 建库与五服务启动脚本都是重复度高、容易出错又耗时的部分，AI 生成初稿后我主要做"核对业务口径 + 补异常用例 + 纠正环境细节"。例如风控的短路顺序（状态→单笔→日累计）和"存款不校验日累计"这两条，AI 初稿会漏，但一旦写进断言，回归就能守住；真实联调时 AI 一开始把 `SERVER_PORT=18080` 设成全局环境变量，导致四个业务服务全挤到 18080 只起来一个，也是我按日志定位后改成"仅网关设 18080"才跑通——这比纯手工快很多，但前提是人要能读懂启动日志。

AI 也有拖慢的地方：一是它容易把"实际输出"写得和"期望输出"一样，看不出真的执行了，我必须逐条到 Surefire 报告里核对返回值与数据库断言；二是它倾向把跨服务联调也一起"代做"，但那些依赖 S2/S5 的环境与权限，不能越俎代庖。这让我更清楚一条底线：**AI 只负责生成"可被验证的初稿"，业务规则和"什么算通过、什么算未执行"必须由人按交接文档拍板**。

如果重做一次，我会先把 S3 的"退出准则"和"哪些不填通过"写成清单再让 AI 生成用例，减少来回返工；对涉及资金语义的断言，坚持由 S2/S5 复核而不是自证。团队约定上，应当继续坚持"资金与风控逻辑至少两人复核、AI 生成内容必须能对应到 Git 提交与测试报告"。
