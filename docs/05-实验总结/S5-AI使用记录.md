## 5. 否决或未采纳的内容

| 内容 | 原因 |
|---|---|
| 按分工表原文把前端写成“只有 README” | 仓库实际有页面源码和 `dist` 产物，与事实不符 |
| 用 H2 或替身结果代替真实 MySQL 记录 | 分工表明确要求真实服务与数据库 |
| 修改 `frontend/README.md` 里的代理端口描述 | 不在本次任务范围内，只报告差异 |
| 预填组内互评分数 | 分工表要求成员确认，不能预填 |
| 把 UNKNOWN 第一次查询仍为 UNKNOWN 判成缺陷 | 实测是异步收敛，轮询后变 SUCCESS，属于观察项 |

## 6. 效率影响与体会

AI 对脚本和证据整理帮助最大。接口脚本和页面脚本都从零写完，并且能直接跑出真实结果。AI 也帮我发现环境细节。比如离线构建失败的原因、网关实际端口是 8090、渠道内部接口需要单独令牌。

AI 也拖慢过进度。页面脚本最初误点了“退出登录”，我连续改了三轮才定位到原因。接口脚本也因为中文 URL 没有编码，出现过 HTTP 0。这些问题不是业务缺陷，而是测试脚本自身的错误。我把过程文件都留在证据目录，没有隐藏。

有一点我记住了。AI 生成的测试判定不能直接使用。页面连续点击那一条，脚本最初判成通过，但页面残留了确认弹窗。我没有把它当成产品缺陷放过，而是加了确认锁，然后重跑验证。现在页面上只有一个确认弹窗。涉及资金和结论的地方，必须回到数据库和原始响应核对。
