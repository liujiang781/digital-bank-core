# 实验三 · 系统原型构建与实现

**目标**：搭建可运行的软件原型，选取部分模块编码实现，打通至少一条端到端业务流程（存款）。

## 写作清单

### 1. 概述
- [ ] 原型构建的总体思路：先做什么、后做什么、为什么这样排
- [ ] 选择实现的模块清单及理由（人力有限，说明取舍）
- [ ] 技术栈与运行环境说明（JDK / Node 版本、启动步骤）

### 2. 模块实现（每个模块一节）
- [ ] `2.1 核心功能展示`：界面原型截图 + 功能/输入/处理/输出说明
- [ ] `2.2 核心代码片段`：1-2 个**最有代表性或最难实现**的代码，附注释

**建议写进报告的代码片段**

| 片段 | 为什么值得写 | 文件位置（待填） |
|---|---|---|
| 转账的事务处理 | 体现一致性设计 | `backend/.../TransferService.java` |
| 幂等校验 | 体现对重复提交的防护 | `backend/.../IdempotentInterceptor.java` |
| 风控规则匹配 | 体现业务规则可扩展性 | `backend/.../RiskEngine.java` |

> 代码片段不超过 40 行，聚焦关键逻辑；不要把整个 Controller 贴上去。

### 3. AI 辅助说明
- [ ] 本节使用的 AI 生成代码，逐处登记到 [../05-实验总结/AI使用记录.md](../05-实验总结/AI使用记录.md)
- [ ] 报告中注明：哪些方法由 AI 生成骨架、人工补了什么、改了什么

## 实现检查清单

- [ ] `docker compose` 或一键脚本能启动全部依赖
- [ ] 数据库初始化脚本随仓库提交（`deploy/sql/schema.sql` + `init-data.sql`）
- [ ] 关键接口有统一返回体与错误码（如 `1001 余额不足`）
- [ ] 后端日志能看出一次转账的完整链路（traceId）
- [ ] 前端有 loading / 错误提示，不要点了没反应

## 常见扣分点

- 只有页面截图，没有可运行代码
- 存款流程都跑不通（这是指导书明确要求的验收点）
- 代码里硬编码数据库密码、把 `.env` 提交上来
- 贴的代码是 AI 生成的默认模板，提问时讲不清逻辑
- 前后端联调用的是写死的假数据，没真正走后端接口
