# 跨行转账 S2 与 S3 联调交接

本文约定模拟跨行转账的 S2 接口和联调验收。代码基线为 `main@625e991`，该版本的 S3 转账实现覆盖本行转账。请 S3 按本文接入跨行分支，联调使用真实服务和隔离的演示库。 [基线提交](https://github.com/liujiang781/digital-bank-core/commit/625e991008d9128858ec260c0a2650ea4b092831) · [原 S2/S3 接口交接](S2-S3接口交接说明.md)

## 1. 分工与接入顺序

1. **S3 接收用户请求。** `POST /api/v1/transfers` 的跨行分支接收 `payerAccountId`、`externalBankCode`、`externalPayeeRef`、`amount`、`currency` 和 `requestId`，`purpose` 可选，`payeeAccountId` 为空。当前前端发送 `payerAccountId`，基线 S3 DTO 使用 `accountId`。公开接口请接受 `payerAccountId` 并兼容旧字段 `accountId`，两个字段同时传入且值不同时返回参数错误。使用登录身份调用 S2 跨行付款方快照做归属检查。 [前端请求](https://github.com/liujiang781/digital-bank-core/blob/625e991/frontend/src/api/transaction.js#L28-L47) · [S3 基线 DTO](https://github.com/liujiang781/digital-bank-core/blob/625e991/backend/transaction-service/src/main/java/com/digitalbank/transaction/dto/TransactionDtos.java#L21-L23)
2. **S3 幂等建单并执行风控。** 用 `(identityId, EXTERNAL_TRANSFER, requestId)` 认领原单，请求指纹纳入付款账户、外部银行、外部收款方引用、金额和币种等请求要素。同键同内容返回同一笔交易，同键异内容返回 `409 REQUEST_CONFLICT`。`transaction` 初始 `business_type=EXTERNAL_TRANSFER`、`status=ACCEPTED`，`account_id` 为付款账户。关联 `transfer_order` 初始 `transfer_type=EXTERNAL`、`clearing_status=SUBMITTED`，填写 `payer_account_id`、`external_bank_code`、脱敏 `external_payee_ref`、金额和币种，`payee_account_id=NULL`。两张单均提交后再调用 S2 预留。`SUBMITTED` 是当前库表允许的初始清算标记，是否已调用渠道以 S3 渠道记录为准。风控把 `EXTERNAL_TRANSFER` 加入出账类型，使用付款方快照及出账单笔、日累计限额。受理前风控拒绝走原 `/failures`，携带本单 `REJECTED` 和 `RISK_EVENT` 凭证。 [数据库约束](https://github.com/liujiang781/digital-bank-core/blob/625e991/deploy/sql/schema.sql#L165-L204) · [风控出账类型](https://github.com/liujiang781/digital-bank-core/blob/625e991/backend/risk-service/src/main/java/com/digitalbank/risk/service/RiskCheckService.java#L25-L27)
3. **S2 预留后，S3 才发起渠道。** 首次预留返回 `PROCESSING` 和 `RESERVED` 才进入渠道提交路径。账户侧拒绝时读取 `reasonCode`。重试发现原单已经推进时，按原单和原渠道记录继续。S3 持久化模拟渠道请求、结果与稳定凭证，用 `CHD` 加 `tradeNo` 作为渠道幂等键。渠道查询、恢复和提交重试沿用该键。待确认时查询既有渠道记录。
4. **S3 上报渠道结果，S2 推进资金状态。** S2 负责余额、预留、流水、`transaction` 的推进字段，以及 `transfer_order.clearing_status` 的后续变化。S3 从资金结果接口读取最终状态，对外展示成功以 S2 的 `SUCCESS` 为准。

建单后固定付款方、银行和外部收款方，使用可稳定关联的脱敏收款方引用。S3 上报前以原渠道记录核对付款人、收款方、金额、币种及结果凭证。S2 校验渠道请求号、资金要素和原单关联，再按可信的 S3 回执记账。

## 2. S3 调用的 S2 接口

从 S3 直连 `ACCOUNT_SERVICE_URL`，本地默认 `http://localhost:8082`。两边配置同一个 `ACCOUNT_INTERNAL_TOKEN`，请求携带 `X-Internal-Token`，并透传 `X-Trace-Id`。JSON 金额使用两位小数的正数字符串，币种使用 `CNY`。

| 方法和路径 | 请求及约束 | 读取结果 |
| --- | --- | --- |
| `POST /internal/v1/accounts/snapshots` | `identityId`、`businessType=EXTERNAL_TRANSFER`、`payerAccountId`。省略 `payeeAccountId` | `data.account` 提供付款方状态、余额和限额，`data.payee` 为 `null` |
| `POST /internal/v1/postings/reserve` | `tradeNo`、`payerAccountId`、`amount`、`currency`。省略 `payeeAccountId` | 首次通过返回 `PROCESSING` + `RESERVED`。账户侧业务拒绝返回 `REJECTED` 和原因 |
| `POST /internal/v1/postings/external-transfer-results` | 回执见下方。原单须已在 S2 受理并预留 | 根据回执写入资金结果 |
| `GET /internal/v1/postings/{tradeNo}` | 原交易号 | 查询已提交的资金状态和预留状态 |
| `POST /internal/v1/postings/failures` | 跨行风控拒绝使用 `tradeNo`、`decision=REJECTED`、`reasonCode`、`evidenceType=RISK_EVENT`、`evidenceId` | 跨行仅在预留前使用此接口 |

跨行成功回执示例。

```json
{
  "tradeNo": "TRD20261117EXT001",
  "payerAccountId": "ACC_S2_001",
  "amount": "100.00",
  "currency": "CNY",
  "result": "SUCCESS",
  "channelRequestId": "CHDTRD20261117EXT001",
  "evidenceId": "EVDEXT001",
  "observedAt": "2026-11-17T15:30:00+08:00",
  "reasonCode": null
}
```

`channelRequestId` 固定为 `CHD` 加原 `tradeNo`，`observedAt` 使用 `+08:00`。明确成功或失败必须提供稳定的 `evidenceId`。`SUCCESS` 的 `reasonCode` 省略或传 `null`。`FAILED` 必填明确失败机器码，例如 `CHANNEL_DECLINED`。`UNKNOWN` 的 `evidenceId` 和 `reasonCode` 可省略。渠道超时、响应丢失或结果未知使用 `UNKNOWN`。

资金接口统一返回 `data={tradeNo,status,reservationStatus,reasonCode}`。外层 `code=SUCCEEDED` 表示命令处理成功，用户交易结果以 `data.status` 为准。

| 渠道或本地处理阶段 | S2 交易状态 | 清算状态 | 资金效果 |
| --- | --- | --- | --- |
| 预留成功 | `PROCESSING` | `SUBMITTED` | 预留增加，账面余额不变，零条流水 |
| 渠道未知 | `UNKNOWN` | `UNKNOWN` | 继续保留同笔预留，账面余额不变，零条流水 |
| 明确成功已登记，扣款尚待完成 | 原 `PROCESSING` 或 `UNKNOWN` | `CONFIRMED_SUCCESS` | 已持久化成功凭证，预留仍有效，可沿原回执重试扣款 |
| 明确失败已登记，释放尚待完成 | `RECOVERING` | `CONFIRMED_FAILURE` | 已持久化失败凭证，预留仍有效，可沿原回执重试释放 |
| 成功扣款已提交 | `SUCCESS` | `CONFIRMED_SUCCESS` | 同一事务扣减付款方账面余额、消费预留，写一条 `TRANSFER_OUT` / `DEBIT` 流水 |
| 失败释放已提交 | `FAILED` | `CONFIRMED_FAILURE` | 释放同笔预留，账面余额不变，零条流水 |

## 3. S3 的查询、重试与恢复

- 模拟渠道对同一 `channelRequestId` 复用既有请求。明确结果确定后持久化其方向、`evidenceId`、失败原因和观测时间，以便 S3 重启后重放。对外交易详情及定时恢复按 `EXTERNAL_TRANSFER` 分派。`UNKNOWN` 查询原渠道结果并再次上报，`RECOVERING` 重放已登记的明确回执以完成 S2 的本地资金动作。 [S3 基线调度](https://github.com/liujiang781/digital-bank-core/blob/625e991/backend/transaction-service/src/main/java/com/digitalbank/transaction/service/RecoveryScheduler.java#L50-L65)
- S2 调用超时或收到 `5xx` 时，先查 `GET /internal/v1/postings/{tradeNo}`。`RECOVERING` 时重放同一明确回执。查询仍是 `PROCESSING` 或 `UNKNOWN` 且 S3 已持久化明确结果时，也可重放该回执。查询已到预期终态时向用户返回当前结果。跨行明确失败走 `external-transfer-results`，该业务的资金释放由 S2 根据渠道回执推进。
- 为跨行明确回执补专门的重试判断。基线的 `AccountClient.sendCommand` 会在查到 `UNKNOWN` 或 `RECOVERING` 时结束重发。将 `RECOVERING` 加入恢复任务的扫描状态，并由 `EXTERNAL_TRANSFER` 分支根据已持久化的渠道记录上报结果。详情查询也按业务类型分派。 [S3 命令重试](https://github.com/liujiang781/digital-bank-core/blob/625e991/backend/transaction-service/src/main/java/com/digitalbank/transaction/client/AccountClient.java#L115-L126) · [S3 恢复扫描](https://github.com/liujiang781/digital-bank-core/blob/625e991/backend/transaction-service/src/main/java/com/digitalbank/transaction/service/RecoveryScheduler.java#L50-L65)
- 同一明确结果、同一凭证的重试可重复调用，失败时沿用原 `reasonCode`。已登记明确回执后，晚到的 `UNKNOWN` 返回当前状态。矛盾的明确回执或变更已登记的凭证会返回 `409 REQUEST_CONFLICT` 并留审计，交人工核对原单和渠道凭证。

## 4. 环境与验收

- **S4** 让 S2 和 S3 使用同一个数据库。S2 复用现有表，账户服务数据库用户需要 `transfer_order` 的 `SELECT`，以及 `clearing_status` 与 `version` 列的 `UPDATE`。交易服务需要该表的 `SELECT`、`INSERT`。若 S3 为模拟跨行渠道新增持久化表，由 S3 提供增量 SQL 给 S4。
- **S5** 公开转账请求使用 `payerAccountId`。跨行结果展示以 S3 返回的 `data.status` 为准，支持 `UNKNOWN` 待确认和 `RECOVERING` 恢复中。

| 联调用例 | 核对结果 |
| --- | --- |
| 明确成功，重复提交同一请求并重放回执 | 同一 `tradeNo`，付款方仅扣一次、预留 `CONSUMED`、仅一条付款方流水。该笔金额继续计入受理日出账额度 |
| 明确失败 | `FAILED` + `RELEASED`，付款方账面余额不变，零条流水 |
| 渠道超时后查到明确结果 | 待确认期间预留有效且无流水，沿原渠道请求核对后按明确结果扣款或释放 |
| 已登记回执，本地记账或释放暂时失败 | 成功回执的本地扣款失败时仍为原 `PROCESSING` 或 `UNKNOWN`，明确失败的释放失败时为 `RECOVERING`。核对预留仍有效，余额和流水无部分提交，再用相同凭证重放至终态 |
| 明确结果冲突或晚到 `UNKNOWN` | 冲突返回 `409`。晚到未知保持已确认的结果，账务只有一次有效变动 |
| 风控或余额不足 | 在渠道调用前拒绝，查询原单状态，核对零预留和零流水 |

联调时请 S3 提供成功、失败、超时三种模拟渠道的触发方法，并保留同一笔请求的 `requestId`、`tradeNo`、`channelRequestId`、`traceId`、回执和查询响应。S2 按 `tradeNo` 核对付款方余额、预留及流水。共享证据时请去掉令牌和完整收款账号。
