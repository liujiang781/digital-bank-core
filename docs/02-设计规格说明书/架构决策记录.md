## ADR-004：前端技术栈

- **状态**：已接受
- **日期**：2026-10-__
- **决策者**：全组（成员 E 整理）
- **关联**：报告 2.1.1、前端故事 US-40—43

### 背景
前端是客户与后台人员操作账户、交易、风控的统一入口（US-40—43）。实验周期约 10 周，组员以课程作业为主，环境稳定性优先于技术新鲜度。

### 候选方案
1. **Vue 3 + Element Plus**：组合式 API，表单/表格组件覆盖账户与交易页面，构建简单。
2. **React + Ant Design**：生态大，但部分组员不熟，排错成本高。
3. **Thymeleaf 服务端渲染**：前后端耦合，复杂交互（流水分页、状态轮询）开发慢。

### 决策
采用 **Vue 3 + Element Plus**。

### 理由
考量优先级为组员熟悉度 > 生态 > 新鲜度。组员多数有 Vue 基础，熟悉度最高。Element Plus 的表单校验、表格分页、消息提示组件可直接覆盖存款/转账/流水页面，开发成本低。放弃 React 是因为部分组员不熟、排错会拖慢实验周期；放弃 Thymeleaf 是因为它把页面绑死在后端模板，不利于与 gateway 的 JWT 前端集成和复杂交互。**不为新技术让全组卡在环境上。**

### 后果
- 正面：上手快、组件全、与后端 JSON 接口对接直接。
- 负面 / 成本：需统一 ESLint 与 Vite 构建配置；首屏与大数据流水列表需做分页与懒加载优化。

## ADR-005：数据库与缓存选型

- **状态**：已接受
- **日期**：2026-10-__
- **决策者**：全组（成员 E 整理）
- **关联**：NFR-02、BR-04、BR-11/12、报告 3.1

### 背景
系统资金一致性要求强一致（NFR-02），每笔资金变动须可追溯、流水只增不改（BR-04），重复请求靠唯一索引去重（BR-11/12）。

### 候选方案
1. **MySQL 8（InnoDB）**：支持本地事务与 ACID，强一致。
2. **MongoDB**：文档灵活，但事务弱，不适合资金。
3. **是否引入 Redis**：仅在"余额查询压力"或"幂等键"有明确需求时引入。

### 决策
主库采用 **MySQL 8（InnoDB）**；**不引入 Redis**。

### 理由
资金一致性强一致要求，MySQL 本地事务即可保证"付款扣账 + 收款入账"原子完成，实现简单且可验证（对应 ADR-002 单库本地事务）。MongoDB 事务弱，不适合资金。Redis 仅在余额查询压力或幂等键有明确需求时引入；当前 P0 并发目标仅 10 名模拟客户（NFR-04），MySQL 可承受，引入 Redis 属过度设计。幂等由 `transaction` 表 `request_id` 唯一索引实现，不依赖 Redis。

### 后果
- 正面：架构简单、一致性有保障、运维成本低。
- 负面 / 成本：高并发下需后续评估读写分离或缓存；若压测不达标再决定是否引入 Redis 缓存余额。
