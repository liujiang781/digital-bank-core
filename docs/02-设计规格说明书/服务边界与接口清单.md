# 服务边界与接口契约

> 编制人：成员 E（接口契约与交付整合）
> 设计依据：实验一《需求规格说明书》整合版 v1.2（docs/01-需求规格说明书/实验一需求规格说明书.md）
> 配套图：docs/uml/class/context-map.puml（四限界上下文关系）

## 1 概述

本系统按限界上下文（Bounded Context）划分为四个业务服务。四个服务分别是 user-service、account-service、transaction-service、risk-service。系统另设一个 gateway 网关。网关负责路由、鉴权和限流。

本清单给出每个服务的职责边界、拥有的数据、对外端点，以及统一的响应体和错误码。接口设计满足需求规格中的业务规则 BR 与非功能需求 NFR。

**服务名一致性说明（依赖项）**：本清单的服务名以 02 设计 README 的建议草案为准。组长编写的 logical-arch.puml（图 2-1 逻辑架构包图）定稿后，若包名有调整，须同步更新本文所有服务名。接口清单的编写依赖图 2-1 定稿，本版先按草案服务名落库，待图 2-1 确认后做一次对齐复核。

## 2 服务职责边界与数据归属

表 2-1 服务职责边界与数据归属。每个服务拥有自己的数据，服务之间不共享数据库。

| 服务 | 职责边界 | 拥有的数据（实体／表） | 对外端点数 | 对应限界上下文 |
| --- | --- | --- | --- | --- |
| user-service | 客户身份、注册、实名、登录认证、资料维护 | customer、credential（realname_info 随 customer） | 3 | User |
| account-service | 账户生命周期、余额与状态、占用金额、开户/冻结/解冻/注销、个人限额 | account、account_status_log、account_daily_limit | 9 | Account |
| transaction-service | 交易受理、存款/取款/本行与跨行转账、流水、幂等、待确认核对与失败恢复 | transaction、transfer_order、fund_entry | 10 | Transaction |
| risk-service | 单笔与日累计限额校验、规则命中、风险记录查询 | risk_rule、risk_event | 4 | Risk |
| gateway | 路由、JWT 鉴权、限流、requestId 透传；不持有业务数据 | — | — | 基础设施（非业务上下文） |

**为什么这样划分**：账户聚合（Account）负责余额与状态，是强一致热点。交易聚合（Transaction）负责流水与幂等，是只增不改的追加写。两者读写模式、锁策略和故障域都不同，因此拆成两个服务（详见 context-map.puml 的论证）。风控（Risk）只做规则校验，不持有资金，独立后可配置化演进。

## 3 统一响应体结构

所有服务通过 HTTP/JSON 通信。响应体统一为 `ApiResponse<T>`，结构如下：

```json
{
  "code": "0",
  "message": "success",
  "data": { },
  "requestId": "7f3c...uuid",
  "traceId": "a1b2...",
  "timestamp": 1761547200000
}
```

字段说明：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| code | string | "0" 表示成功；非 "0" 表示业务错误，取值见第 5 节错误码 |
| message | string | 给操作人员或前端提示的中文文案，不直接拼接 SQL 或内部异常 |
| data | object | 业务数据；失败时可为 null |
| requestId | string | 透传客户端幂等键 X-Request-Id，便于对账与排错 |
| traceId | string | 链路追踪编号，跨服务串联一次请求 |
| timestamp | long | 响应生成时间，毫秒时间戳 |

成功约定：HTTP 状态码为 200，业务 `code="0"`。业务校验失败约定：HTTP 状态码随错误码而定（400/401/403/409/429/500/504），响应体 `code` 填业务错误码，`data` 可为 null。

## 4 requestId 幂等约定

需求规格 BR-11/12、NFR-02 要求同一请求重复提交只产生一次资金效果。约定如下：

1. 客户端（前端）在每次写请求生成 `requestId`（UUID v4），放入请求头 `X-Request-Id`。
2. gateway 校验头存在后透传到下游服务，并写入 `ApiResponse.requestId`。
3. transaction-service 将 `request_id` 作为 `transaction` 表的唯一索引列。
4. 同一 `requestId` 重复提交：数据库唯一约束拦截，服务直接返回首次结果（HTTP 200 + 原 `data`），不再做第二次资金动作。
5. 同一 `requestId` 但内容不同：返回 409，错误码 `TRX-002`（冲突），不执行。
6. 幂等范围覆盖所有写操作：存款、取款、本行转账、跨行转账、冻结/解冻、注销。
7. 只读查询（余额、流水）不要求幂等键，但建议仍透传以便追踪。

## 5 错误码规范与 BR 对应关系

错误码格式为 `<域>-<四位编号>`，如 `ACC-002`。域分类：AUTH（认证授权）、ACC（账户）、TRX（交易）、RISK（风控）、SYS（系统）。

表 2-2 错误码与业务规则对应关系。

| 错误码 | HTTP | 含义 | 对应 BR / NFR | 触发位置 |
| --- | --- | --- | --- | --- |
| AUTH-001 | 401 | 未登录或令牌失效 | NFR-07 | gateway / user-service |
| AUTH-002 | 403 | 越权访问他人数据 | NFR-01、BR-20 | 各服务 |
| AUTH-003 | 400 | 登录凭证错误 | — | user-service |
| AUTH-004 | 423 | 登录失败过多，账户锁定 | — | user-service |
| ACC-001 | 400 | 账户不存在 | — | account-service |
| ACC-002 | 409 | 账户已冻结，禁止新出账 | BR-03 | account-service |
| ACC-003 | 400 | 余额或可用余额不足 | BR-02、BR-04 | account-service |
| ACC-004 | 400 | 超过开户数量上限（3 个） | BR-02 | account-service |
| ACC-005 | 409 | 账户非零余额/有占用/有未决业务，无法注销 | BR（注销规则） | account-service |
| TRX-001 | 400 | 金额非法（≤0、超两位小数、非 CNY） | BR-01 | transaction-service |
| TRX-002 | 409 | 重复请求（幂等冲突） | BR-11/12、NFR-02 | transaction-service |
| TRX-003 | 400 | 超过单笔出账限额 | BR-05 | risk-service / transaction-service |
| TRX-004 | 400 | 超过日累计出账限额 | BR-05 | risk-service / transaction-service |
| TRX-005 | 409 | 本行转账单边失败 | BR-15 | transaction-service |
| TRX-006 | 409 | 跨行转账终态不可重复变更 | BR-16/17 | transaction-service |
| TRX-007 | 400 | 冻结账户禁止新存款/出账/转入 | BR-03 | account-service / transaction-service |
| RISK-001 | 409 | 风控拒绝（限额/频次命中） | BR-05 | risk-service |
| RISK-002 | 404 | 风险记录不存在 | — | risk-service |
| SYS-001 | 500 | 服务内部错误 | NFR-06 | 各服务 |
| SYS-002 | 504 | 外部渠道超时，转入待确认 | NFR-05、BR-16 | transaction-service |
| SYS-003 | 429 | 触发限流 | — | gateway |

### 6.5 gateway（基础设施，非业务端点）

gateway 不提供业务端点。它做三件事：

1. 路由：按路径前缀转发到对应服务（`/api/user/*`→user-service，其余类推）。
2. 鉴权：校验 JWT；无 token 返回 AUTH-001，越权返回 AUTH-002。
3. 限流：对写接口按客户维度限流，触发返回 SYS-003。
4. 透传 `X-Request-Id` 到下游，保证幂等键贯穿全链路。

## 8 网关与鉴权约定补充

- 认证方式：JWT（access token）。未登录访问受保护接口返回 AUTH-001。
- 权限模型：客户仅能访问本人 `customerId`/`accountNo`；后台人员按角色与对象范围授权，越权返回 AUTH-002（对应 NFR-01、BR-20）。
- 敏感字段脱敏：卡号、证件号、手机号按权限脱敏（对应 NFR-09）。
- 审计：冻结、解冻、注销、限额变更、核对、恢复均记录操作者、时间、对象、原因与结果（对应 NFR-10）。
