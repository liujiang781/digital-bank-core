# 架构决策记录（ADR）

> ADR-001、002 为组长设计决定；全组架构评审及各成员对接口和数据库的交叉确认仍需进行。

## ADR-001：架构风格

- **状态**：已接受（组长设计基线，待全组评审）
- **日期**：2026-10-27
- **决策者**：组长

### 背景
五人组、两周设计工期，需要展示 user、account、transaction、risk 四个业务边界及独立节点，并保证资金一致性。

### 候选方案

| 维度 | 微服务 | 单体分层 | 模块化单体 |
|---|---|---|---|
| 边界 | 独立部署及接口 | 包约定 | 进程内模块约束 |
| 一致性 | 跨服务困难；可集中资金写入 | 单库本地事务简单 | 单库本地事务简单 |
| 开发调试 | 高，多进程和网络故障 | 低 | 中 |
| 部署运维 | 高，多节点及日志 | 低 | 较低 |
| 五人组 | 可并行但需协调 | 容易上手 | 并行和边界较平衡 |
| 两周 | 紧张，需控制范围 | 可行 | 可行 |

### 决策
采用轻量四服务：user-service、account-service、transaction-service、risk-service；经 gateway 统一入口。账户服务统一执行本行资金写入。四个服务可共用数据库实例，但应按数据职责限定写入权限，不能将物理分库或独立数据所有权视为已实现。

### 理由
任务明确要求四个业务服务独立部署，四服务可体现子域和团队分工。单体分层开发最省事，但不满足上述部署交付约束；模块化单体更适合小团队，却无法直接展示四个独立服务节点。此选择以课程交付为前提，不以技术流行为理由。

### 后果
- 可明确服务接口与部署责任，资金原子操作有单一写入方。
- 增加网络、调试、部署及接口治理成本；远程调用可能超时，须处理重试、重复请求和故障恢复。共享实例带来耦合和单点，权限隔离及恢复要单独验证；不能据此宣称生产级高可用。Redis 仍待 ADR-005 决定。

## ADR-002：本行转账一致性

- **状态**：已接受（组长设计基线，待全组评审）
- **日期**：2026-10-27
- **决策者**：组长

### 背景
根据整合版 v1.2 的 BR-15，付款扣账、收款入账及双方关联流水须一致；BR-11/12 要求幂等，BR-04 要求余额与占用保持不变式。交易编排和账户是不同服务，不能假定跨 HTTP 调用存在一个事务。

### 候选方案

| 方案 | 适用性与代价 |
|---|---|
| 单库本地事务 | 所有资金写入集中在账户服务主库事务中，容易验证原子性；牺牲写入独立性 |
| 编排式 Saga | 支持跨服务自治，但补偿期间可能出现中间状态，故障恢复与资金可见性更复杂 |
| TCC | 可显式预留和取消，但需三阶段接口、空回滚、防悬挂及恢复机制 |

### 决策
本行转账选单库本地事务：交易服务发出命令，账户服务在主库事务内以固定顺序锁定双方账户和相关限额记录，复核规则并写入预留、双方余额、流水和幂等结果；所有写入一起提交或回滚。请求唯一约束、内容比较与事务内结果记录防止并发重放。客户端超时后按同一请求标识查询或重试，不能假设事务已经失败。模拟跨行仍需单独的预留、待确认和恢复流程，不能将外部调用放在本地数据库事务内。

### 理由
本行两侧账户属于同一资金写入边界，单库事务能直接满足 BR-15 且便于测试。Saga 补偿不能替代双方同时成立；TCC 可实现但相对课程工期引入过多状态及恢复代码。

### 后果
- 原子提交便于验证，失败回滚不会留下单边资金变动。
- 账户服务承担记账与相关结果写入，数据所有权和 D 的表设计需明确；锁竞争、死锁重试、并发限额以及数据库故障需测试。主从异步复制可能延迟，资金判断和结果确认必须读主库；不能声称主从切换无损。
