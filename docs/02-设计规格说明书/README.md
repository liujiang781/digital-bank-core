# 实验二 · 设计规格说明书

**目标**：给出满足问题描述与约束条件的系统解决方案，用 UML 建立设计模型。

> 本实验的**核心得分点**是"架构方案对比与选型理由"（报告 2.1.1）和"逻辑架构 + 物理架构"两张图。
> 选型过程单独记到 [架构决策记录.md](架构决策记录.md)，报告正文只放结论。

## 写作清单

### 1. 概述
- [ ] 总体设计思路、设计内容、与技术选型的对应关系（300-500 字）

### 2. 总体设计
- [ ] `2.1.1 架构决策与选型`：**至少对比两种架构方案**
  - 候选一：**微服务架构**（Spring Cloud / Nacos / Gateway）
  - 候选二：**单体分层架构**（Spring Boot + 分层包）
  - 候选三（可选）：**模块化单体**（Modular Monolith）
  - 对比维度：开发复杂度、部署运维成本、一致性保障难度、团队规模匹配度、实验周期可行性
  - 结论要给出**为什么选 A 而不选 B**，不要写"微服务很流行所以选微服务"
- [ ] `2.1.2 系统逻辑架构` → **包图**：`../uml/package/logical-arch.puml`
- [ ] `2.1.3 系统物理架构` → **部署图**：`../uml/deployment/physical-arch.puml`
  - 至少体现：浏览器 / Nginx / Gateway / 各微服务 / MySQL / Redis /（可选）MQ

### 3. 模块设计

### 4. 数据库设计
- [ ] `3.1` 类模型 → 关系表的映射方案（继承、组合、多对多怎么转）

## 建议的服务划分（草案，需经领域建模论证）

| 服务 | 职责边界 | 拥有的数据 |
|---|---|---|
| user-service | 客户信息、认证 | customer, credential |
| account-service | 账户生命周期、余额 | account, account_status_log |
| transaction-service | 交易受理、流水、幂等 | transaction, transfer_order |
| risk-service | 限额与规则校验 | risk_rule, risk_event |
| gateway | 路由、鉴权、限流 | — |

> 服务边界要能说清"为什么这个实体归这个服务"，报告里最好用一张**上下文映射图**表达。

## 常见扣分点

- 只写"采用微服务架构"，没有对比方案，没有约束分析
- 包图只有三层（controller/service/dao），没有业务子域划分
- 部署图把数据库和所有服务画在同一台机器上，与"分布式"结论矛盾
- 设计类清单与序列图里的类名不一致
- 库表设计与类模型脱节：类图有关联类，表里直接丢了
