**复用约定**：

- `AccessService`：统一身份、操作权和对象范围检查；C 传入 `operation=INTERNAL_TRANSFER`，付款账户必须是本人账户，收款账户只校验存在与状态，不要求归属。

- 实体只使用 B 的字段与操作；C 不重新定义 `Account`、`Transaction`、`FundEntry`、`TransferOrder`、`RiskRule`、`RiskEvent` 的字段名。

## 3 用例实现

### 3.1 UC-TR-03 本行转账（图 2-7、图 2-8）

**主成功路径**：

1. `TransferForm` 收集付款账户、收款账户、金额、用途，提交 `requestId`；`TransferController` 从会话取身份，调用 `AccessService.authenticate()`。
2. `AccessService.requireAccountAccess(INTERNAL_TRANSFER, payerAccountId)` 校验付款账户归属；`TransferService` 读取收款账户，校验存在、非同一账户、币种一致（BR-20/BR-15）。
3. `IdempotencyService.claimOrLoad(identityId, INTERNAL_TRANSFER, requestId, requestHash)`：
   - `EXISTING_SAME`：返回原 `Transaction.snapshot()`，不重复扣款/入账；
   - `CONFLICT`：409 `REQUEST_CONFLICT`；
   - `NEW`：继续。
4. 金额合法性（BR-01）：CNY、> 0、小数 ≤ 2 位。非法金额只由 `IdempotencyService.complete()` 记录技术拒绝，**不创建 Transaction，不写 FundEntry**。
5. 金额合法后创建 `Transaction(RECEIVED)`，`accountId=payerAccountId`、`businessType=INTERNAL_TRANSFER`、`requestId`、`requestHash`。
6. `RiskCheckService.checkOutgoing(...)`：
   - 付款方/收款方状态非 `NORMAL`（BR-03）→ 写 `RiskEvent`（`ruleId=RK-01`，`ruleVersion=1`，`reasonCode=ACCOUNT_STATUS`，`result=REJECT`）→ `Transaction.markRejected()`；不写 `FundEntry`。
   - `RiskRule.evaluateOutgoing(amount, snapshot)` 超单笔（BR-05/06）或超日累计（BR-05/07）→ 写 `RiskEvent`（`ruleId=limitRule.ruleId`，`ruleVersion=limitRule.ruleVersion`，`reasonCode=SINGLE_LIMIT/DAILY_LIMIT`，`result=REJECT`）→ `Transaction.markRejected()`；不写 `FundEntry`。
   - 通过 → 创建 `TransferOrder(INTERNAL, NOT_APPLICABLE)`，付款/收款账户、金额、币种与 Transaction 一致。
7. `PostingService.reserve(payerAccountId, amount, tradeNo)`：`Account.reserve(amount)`（R 增加、B 不变），`Transaction.markProcessing()`，记录 `acceptedAt`；按受理日占用额度（BR-14/05/06/07）。
8. `PostingService.postInternalTransfer(tradeNo, payer, payee, amount)`：在同一资金提交边界内锁定双方账户，`payer.debitReserved(amount)`（B/R 同减）、`payee.credit(amount)`（B 增），写 `FundEntry(TRANSFER_OUT)` 与 `FundEntry(TRANSFER_IN)`，`Transaction.markSucceeded()`（BR-15/19）。
9. 返回 `TransferResult(tradeNo, SUCCEEDED)`；双方流水共用 `tradeNo`，可按 `FundEntry` 追溯。

**异常分支**：

| 分支 | 触发 | 处理 | 资金结果 |
|---|---|---|---|
| 未认证/越权 | 非本人付款账户 | 401/403，不泄露他人账户 | 无变化 |
| 幂等重放 | 同三元组、同 `requestHash` | 返回原 `Transaction.snapshot()` | 不重复 |
| 幂等冲突 | 同三元组、不同 `requestHash` | 409 `REQUEST_CONFLICT` | 无变化 |
| 金额非法 | BR-01 | 技术拒绝；不建 Transaction/ FundEntry | 无变化 |
| 账户不存在/同账户/币种不符 | BR-15/20 | `Transaction.markRejected()` | 无变化，不写 FundEntry |
| 冻结/注销 | BR-03 | 写 `RiskEvent`；`Transaction.markRejected()` | 无变化，不写 FundEntry |
| 单笔/日累计超限 | BR-05/06/07 | 写 `RiskEvent`；`Transaction.markRejected()` | 无变化，不写 FundEntry |
| 双账户提交失败 | 付款扣减或收款入账任一步失败 | 本地提交边界回滚；`PostingService.releaseReservation` | 双方 B/R 回到本次之前 |
| 释放失败 | 数据库异常 | `Transaction.markRecovering()` | R 暂时保留，按 tradeNo 重试 |
| 交易状态落库失败 | 资金已动但状态未更新 | 按 tradeNo 对账/恢复，不重复扣款 | 由恢复收敛 |

> **与图 2-10 的边界**：图 2-10 是组长的跨账户一致性主流程（受理校验 → 预留 → 扣款 → 入账 → 失败释放）。图 2-8 只展开服务交互；两图冲突时以图 2-10 为准。

### 3.2 风控拦截（图 2-9、图 2-11）

**短路顺序**：

1. **金额合法性（BR-01）**：由 `TransferService` 前置完成；非法金额不进入风控、不建 Transaction。
2. **账户状态（BR-03）**：`RiskCheckService` 读取付款方/收款方 `Account.status`；非 `NORMAL` 写 `RiskEvent(RK-01, ACCOUNT_STATUS, REJECT)`。
3. **单笔限额（BR-05/06）**：`RiskRule.evaluateOutgoing` 取 `min(outgoingSingleLimit, personalSingleLimit)`；超限写 `RiskEvent(ruleId, SINGLE_LIMIT, REJECT)`。
4. **日累计限额（BR-05/07）**：当日已成功 + 已占用 + 本笔 > `min(outgoingDailyLimit, personalDailyLimit)`；超限写 `RiskEvent(ruleId, DAILY_LIMIT, REJECT)`。
5. 通过返回 `PASS`，`TransferService` 才创建 `TransferOrder` 并调用 `PostingService.reserve`。

**留痕边界**：

- `RiskEvent` 采用 B 的字段：`eventId`、`tradeNo`、`ruleId`、`ruleVersion`、`operatorIdentityId`、`occurredAt`、`reasonCode`、`result`。
- 账户状态使用内置规则 `RK-01`、`ruleVersion=1`；限额使用 `RiskRule` 的 `LIMIT_POLICY` 行与命中版本。
- 拒绝时 `Transaction` 置 `REJECTED`，**不写 `FundEntry`**，不改变 B/R（BR-19）。
- 高频交易标记为 P2 候选，不在本次核心 `RiskDecision` 中建模；核心只保留 `PASS/REJECT`。

### 3.3 幂等校验（图 2-12）

`IdempotencyService.claimOrLoad` 的判定：

| 情况 | 返回 | 处理 | 资金效果 |
|---|---|---|---|
| 无记录 | `NEW` | 原子认领；进入金额/账户/风控校验 | 尚未产生 |
| 同三元组、同 `requestHash` | `EXISTING_SAME` | 返回原 `Transaction.snapshot()`；处理中返回当前状态 | 不产生第二次 |
| 同三元组、不同 `requestHash` | `CONFLICT` | 409 `REQUEST_CONFLICT` | 不产生 |
| 并发同三元组 | 唯一键冲突 | 回查后按上两行处理 | 不产生第二次 |

**要点**：

1. 幂等键为 B 的 `(identityId, businessType, requestId)`；`requestHash` 是规范化业务内容的 SHA-256，金额 `10`、`10.0`、`10.00` 语义相同，`10.001` 不能四舍五入后接受。
2. 先鉴权再查重；不能因为命中 `requestId` 就绕过 `AccessService`。
3. `claimOrLoad` 必须持久、原子；只“先查再插”不构成并发幂等。
4. `complete()` 记录可重建结果；非法金额等技术拒绝可以有 tradeNo 为空。
5. 终态不可重开：`SUCCEEDED`/`FAILED`/`REJECTED` 后同一三元组只返回原结果；新业务用新 `requestId`。

## 4 关键程序逻辑

### 4.1 预留、双账户提交与释放（BR-14/15）

**预留**（只改 R，不改 B）：

```java
@Transactional
public PostingOutcome reserve(String payerAccountId, BigDecimal amount, String tradeNo) {
    Account payer = accountRepository.lockById(payerAccountId);
    if (payer.getStatus() != AccountStatus.NORMAL) {
        return PostingOutcome.reject("ACCOUNT_STATUS_INVALID"); // BR-03
    }
    if (amount.compareTo(payer.availableBalance()) > 0) {
        return PostingOutcome.reject("INSUFFICIENT_AVAILABLE_BALANCE"); // BR-01/04
    }
    if (!riskRule.evaluateOutgoing(amount, payer.snapshot()).isPass()) {
        return PostingOutcome.reject("LIMIT_EXCEEDED"); // BR-05/06/07
    }
    payer.reserve(amount);          // R += amount; B 不变
    accountRepository.save(payer);
    transactionRepository.markProcessing(tradeNo); // acceptedAt = now
    return PostingOutcome.ok();
}
```

**双账户提交**（同一资金提交边界）：

```java
@Transactional
public PostingOutcome postInternalTransfer(String tradeNo, String payerId,
                                           String payeeId, BigDecimal amount) {
    // 固定按 accountId 升序加锁，避免双向转账死锁
    Account first  = accountRepository.lockById(min(payerId, payeeId));
    Account second = accountRepository.lockById(max(payerId, payeeId));
    Account payer = first.getAccountId().equals(payerId) ? first : second;
    Account payee = first.getAccountId().equals(payeeId) ? first : second;

    if (payer.getReservedAmount().compareTo(amount) < 0) {
        throw new InvalidReservationException(tradeNo);
    }
    payer.debitReserved(amount);    // B -= amount; R -= amount
    payee.credit(amount);           // B += amount

    fundEntryRepository.save(FundEntry.debitOf(tradeNo, payerId, amount, payer.getBookBalance()));
    fundEntryRepository.save(FundEntry.creditOf(tradeNo, payeeId, amount, payee.getBookBalance()));
    transactionRepository.markSucceeded(tradeNo);
    return PostingOutcome.COMMITTED;
}
```

**释放**：

```java
@Transactional
public PostingOutcome releaseReservation(String payerId, BigDecimal amount, String tradeNo) {
    Account payer = accountRepository.lockById(payerId);
    if (payer.getReservedAmount().compareTo(amount) < 0) {
        throw new InvalidReservationException(tradeNo);
    }
    payer.release(amount);          // R -= amount; B 不变
    accountRepository.save(payer);
    // 不写 FundEntry：本次没有实际资金变动（BR-19）
    return PostingOutcome.RELEASED;
}
```

**失败与恢复**：

- `postInternalTransfer` 任一步失败，资金提交边界整体回滚，双方 B/R 不变；随后 `releaseReservation` 释放预留。
- 释放失败：`Transaction.markRecovering()`；按 `tradeNo` 幂等重试，不能重复释放。
- 资金已动但状态落库失败：按 `tradeNo` 查 `FundEntry` 是否已存在，再决定补状态或恢复；不能再次扣款。
- 冻结发生在受理之后：不取消已受理交易，仍按原路径完成或释放（BR-03）。

### 4.2 风控规则匹配（BR-01/03/05/06/07）

```java
public RiskDecision checkOutgoing(Account payer, Account payee, Money amount,
                                  String tradeNo, String identityId) {
    if (!amount.isCny() || amount.value().compareTo(BigDecimal.ZERO) <= 0
            || amount.scale() > 2) {
        return RiskDecision.REJECT_INVALID_AMOUNT; // 由 TransferService 前置处理
    }
    if (payer.getStatus() != NORMAL || payee.getStatus() != NORMAL) {
        riskEventRepository.save(RiskEvent.reject(
            tradeNo, "RK-01", 1, identityId, "ACCOUNT_STATUS")); // BR-03
        return RiskDecision.REJECT;
    }
    RiskRule rule = riskRuleRepository.currentLimitPolicy();
    RiskDecision decision = rule.evaluateOutgoing(amount, payer.snapshot());
    if (!decision.isPass()) {
        riskEventRepository.save(RiskEvent.reject(
            tradeNo, rule.getRuleId(), rule.getRuleVersion(), identityId,
            decision.getReasonCode())); // SINGLE_LIMIT / DAILY_LIMIT
    }
    return decision;
}
```

`RiskRule.evaluateOutgoing` 使用 B 的字段：`outgoingSingleLimit`、`outgoingDailyLimit`、`Account.personalSingleLimit`、`Account.personalDailyLimit`；账户状态是固定业务前置条件，不依赖可配置规则开关。

### 4.3 幂等校验（BR-11/12）

```java
public TransferResult createTransfer(TransferCommand cmd) {
    Identity identity = accessService.authenticate();
    accessService.requireAccountAccess(INTERNAL_TRANSFER, cmd.payerAccountId());

    String hash = RequestHasher.sha256(canonical(cmd));
    IdempotencyDecision decision = idempotencyService.claimOrLoad(
        identity.identityId(), BusinessType.INTERNAL_TRANSFER, cmd.requestId(), hash);

    if (decision == EXISTING_SAME) {
        return TransferResult.replay(transactionRepository.findByKey(
            identity.identityId(), BusinessType.INTERNAL_TRANSFER, cmd.requestId()));
    }
    if (decision == CONFLICT) {
        throw new RequestConflictException(cmd.requestId());
    }
    // NEW：金额校验 -> 建 Transaction -> 风控 -> 预留 -> 提交
    return doCreateTransfer(identity, cmd, hash);
}
```

**为什么不是只加唯一索引**：唯一索引只能阻止重复插入交易，不能阻止重复调用 `PostingService`；`claimOrLoad` 必须先原子认领，后续资金动作再按 `tradeNo` 幂等。

## 5 状态机与错误码

### 5.1 状态（采用 B 的枚举）

`TransactionStatus`：`RECEIVED`、`REJECTED`、`PROCESSING`、`PENDING`、`SUCCEEDED`、`RECOVERING`、`FAILED`。`SUCCEEDED`/`FAILED`/`REJECTED` 为终态。

| 当前 | 事件 | 下一状态 | 资金副作用 |
|---|---|---|---|
| RECEIVED | 权限/金额/账户/风控拒绝 | REJECTED | 无；不写 FundEntry |
| RECEIVED | 预留成功 | PROCESSING | R 增加；B 不变 |
| PROCESSING | 双账户提交成功 | SUCCEEDED | 付款 B/R 同减，收款 B 增；两条 FundEntry |
| PROCESSING | 提交失败且释放成功 | FAILED | R 减回；B 不变；不写 FundEntry |
| PROCESSING | 提交失败且释放失败 | RECOVERING | R 暂时保留 |
| RECOVERING | 幂等重试释放成功 | FAILED | R 减回；不写 FundEntry |
| PROCESSING | 跨行外部结果未知 | PENDING | 保留 R；不提前扣账（扩展点） |
| PENDING | 明确成功/失败/恢复 | SUCCEEDED / FAILED / RECOVERING | 按对应路径 |

`TransferOrder.clearingStatus`：`NOT_APPLICABLE`（本行）、`SUBMITTED`、`UNKNOWN`、`CONFIRMED_SUCCESS`、`CONFIRMED_FAILURE`。本行转账只使用 `NOT_APPLICABLE`，不设独立订单状态。

### 5.2 错误码

| HTTP | 错误码 | 触发 | BR | 资金结果 |
|---|---|---|---|---|
| 400 | `INVALID_ARGUMENT` | 金额/币种/账户格式非法 | BR-01 | 无变化 |
| 401 | `UNAUTHENTICATED` | 未登录或令牌失效 | BR-20 | 无变化 |
| 403 | `FORBIDDEN` | 越权访问他人账户 | BR-20 | 无变化，不泄露归属 |
| 404 | `ACCOUNT_NOT_FOUND` | 账户不存在或无权访问 | BR-20 | 无变化 |
| 409 | `REQUEST_CONFLICT` | 同三元组不同 `requestHash` | BR-11/12 | 无变化 |
| 422 | `ACCOUNT_STATUS_INVALID` | 付款方/收款方冻结/注销 | BR-03 | 无变化 |
| 422 | `INSUFFICIENT_AVAILABLE_BALANCE` | A = B - R < amount | BR-01/04 | 无变化 |
| 422 | `SINGLE_LIMIT_EXCEEDED` | 超 min(outgoingSingleLimit, L1) | BR-05/06 | 无变化 |
| 422 | `DAILY_LIMIT_EXCEEDED` | 超 min(outgoingDailyLimit, Ld) | BR-05/07 | 无变化 |
| 200 | `SUCCEEDED` | 双账户提交完成 | BR-15 | 付款扣减、收款增加、两条 FundEntry |
| 200 | `FAILED` | 受理后失败且释放完成 | BR-15 | 双方回到本次之前 |
| 202 | `PROCESSING` / `RECOVERING` / `PENDING` | 处理中/恢复中/待确认 | BR-14/16/17 | 保留占用，等待收敛 |
| 500 | `INTERNAL_ERROR` | 未预期异常 | — | 不静默丢资金；进入对账/恢复 |
