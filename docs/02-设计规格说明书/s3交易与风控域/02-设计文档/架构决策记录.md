## ADR-003：交易幂等方案（BR-11/12）

- **状态**：已接受
- **日期**：2026-10-27
- **决策者**：C（交易与风控域）
- **复核**：组长 A（PR Review）
- **关联**：BR-11/12、NFR-02、UC-TR-03/04、报告 2.2.2、图 2-12

### 背景

转账、取款、跨行付款都要求“同一请求只能产生一次资金效果”。前端防重复点击只能改善体验，网络重试、超时重发、外部回执重复到达仍可能造成重复扣款或重复入账。需求规格说明书整合版 v1.2 表 1-3 的 BR-11/12 要求：同一身份、业务类型和 `requestId` 的相同请求只处理一次并返回原结果；同一标识对应不同内容必须报冲突；`tradeNo` 贯穿资金处理、外部请求、回执、流水和核对。实验周期只有两周，方案必须可验证、少引入运维组件。

### 候选方案

| 维度 | 方案 A：`(identity_id, business_type, request_id)` 唯一索引 + 内容指纹 | 方案 B：Redis 分布式锁 + 幂等键 | 方案 C：数据库乐观锁（`version`） |
|---|---|---|---|
| 防重复原理 | 三元组唯一约束，插入冲突即重复 | `SETNX` 抢锁，锁内查/写幂等键，TTL 24h | 版本号 CAS，更新时发现版本变化则重试/失败 |
| 同标识不同内容 | `request_hash` 比较，天然可判冲突 | 需要额外保存并比较请求内容 | 不能直接判断，需要额外查历史内容 |
| 并发安全 | 数据库唯一约束兜底，单库可靠 | 依赖 Redis 可用性与锁过期，存在锁续期问题 | 只能防并发更新，不能防重复插入 |
| 新增组件 | 无 | 需部署 Redis、处理序列化/TTL/故障 | 无 |
| 实现与调试成本 | 低，一条 DDL + 一次插入捕获 | 中高，需处理锁误删、过期、脑裂 | 中，重试逻辑分散在更新路径 |
| 与课程项目匹配 | 高，单 MySQL 实例即可验证 | 低，Redis 无明确业务需求（ADR-005） | 中，适合余额更新，不适合作为请求幂等主方案 |
| 两周工期可行性 | 高 | 低 | 中 |

### 决策

采用 **方案 A：`transaction` 表 `UK(identity_id, business_type, request_id)` + `request_hash` + `IdempotencyService.claimOrLoad` 原子认领**。

具体约定：

1. `requestId` 由前端生成 UUID；幂等键按 BR-11/12 使用 `(identity_id, business_type, request_id)`，在 `transaction` 表建唯一索引。三元组唯一键是必需项；`UK(request_id)` 只能作为额外保护，不能替代三元组。
2. `transaction.request_hash` 保存规范化请求内容（账户、金额、币种、备注、业务类型）的 SHA-256；同一三元组命中时比较该值。
3. `IdempotencyService.claimOrLoad` 在独立事务中原子认领并提交，再调用 `PostingService`；避免“下游已预留、本地回滚”导致幂等记录丢失。
4. `EXISTING_SAME` 返回原 `Transaction.snapshot()`；`CONFLICT` 返回 409 `REQUEST_CONFLICT`，不覆盖原结果。
5. 并发插入同一三元组时，由唯一键冲突兜底：捕获 `DuplicateKeyException` 后回查，再按 `request_hash` 比较返回原结果或冲突。
6. 账户入账、扣账、占用、释放、外部请求、回执处理各自再按 `tradeNo` 做一次幂等，不能只靠交易表唯一键。
7. D 的表 2-3 必须按 `UK(identity_id, business_type, request_id)` 落库；`UK(request_id)` 只能作为额外保护，不能替代三元组。
8. `IdempotencyDecision` 仅 `NEW` / `EXISTING_SAME` / `CONFLICT`，与 B 的 `IdempotencyService` 契约一致；`complete()` 只记录可重建结果，不替代 `Transaction` 主状态。

### 理由

**为什么选 A：** 课程项目是单 MySQL 实例，唯一索引是最小、最直接、最容易验证的并发控制；它不依赖额外中间件，失败模式清楚（冲突→回查），且 `request_hash` 能完整表达 BR-11/12 的“同标识同内容/不同内容”两种语义。三元组键与 BR-11/12 的“身份 + 业务类型 + requestId”逐字对应，避免不同客户或不同操作类型之间的标识碰撞。幂等记录先提交，可以把“请求是否受理”与“资金动作是否完成”分开，后续失败走状态机恢复，而不是靠回滚假装没发生。

**为什么不选 B：** Redis 锁解决的是“同一时刻只让一个请求进入”，但锁过期、续期、误删、Redis 故障都会引入新的不一致；本项目没有明确的 Redis 使用需求，ADR-005 也要求“无明确需求即不引入”。用 Redis 会增加部署、调试和答辩解释成本，收益却不如数据库唯一约束直接。

**为什么不选 C：** 乐观锁适合保护 `account.bookBalance` 这类并发更新，但它不能阻止重复插入交易记录，也不能区分同标识不同内容；把它当幂等主方案需要额外的历史查询和重试逻辑，复杂度和方案 A 相近，正确性却更难证明。最终设计中 `version` 仍用于账户与订单更新，但不作为请求幂等的主机制。

### 后果

- **正面**：
  - 幂等判定有数据库唯一约束兜底，单库场景可证明不会重复插入交易；
  - 三元组键与 BR-11/12 的身份、业务类型、requestId 一一对应，跨客户/跨操作类型不会误判；
  - 同标识不同内容有明确 409，不会静默覆盖原结果；
  - 不新增 Redis，部署与实验环境保持一致；
  - 幂等记录先提交，失败后可查询、可恢复，符合“已接收/处理中/失败”的可解释反馈。
- **负面 / 需要承担的成本**：
  - 每次请求多一次数据库写入与一次内容哈希计算；
  - `request_hash` 的规范化规则必须固定（字段顺序、金额格式、空值处理），否则同内容会被误判为不同内容；
  - 幂等记录不能随意删除，需按课程演示周期保留；若未来数据量增大，要做归档而不是直接清理；
  - 唯一索引只能防“同一数据库”的重复，若未来拆成多库，需要额外的全局唯一键或路由规则；
  - 需要处理 `DuplicateKeyException` 的回查竞态：冲突后回查可能短暂查不到（事务未提交），要有有限重试；
  - 方案 A 不能替代资金动作自身的幂等，账户入账/扣账/释放仍需按 `tradeNo` 做条件更新；
  - 三元组索引比单列 `request_id` 索引更宽，写入与存储成本略高，但换来与 BR-11/12 一致的语义。

### 验证方式

1. 同一身份、同一业务类型、同一 `requestId` 与相同内容连续提交 3 次：只产生 1 个 `tradeNo`、1 次预留、1 次扣款/入账、1 组 FundEntry。
2. 同一三元组修改金额后提交：返回 409，原交易状态与资金不变。
3. 两个线程并发提交同一三元组：一个成功插入，另一个捕获唯一键冲突并返回原结果；账户只变化一次。
4. 不同客户使用相同 `requestId` 字符串：因 `identity_id` 不同而互不冲突；若采用全局 `UK(request_id)`，必须保证前端 UUID 全局唯一。
5. 下游 `PostingService` 超时后重试同一三元组：不重复预留；按 `tradeNo` 查询当前状态并继续或恢复。
6. 外部回执重复到达：按 `tradeNo` 幂等，不产生第二次入账/扣账。
