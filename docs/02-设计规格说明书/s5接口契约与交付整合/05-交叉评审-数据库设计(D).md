## 结论

整体结构完备：10 张表都有类模型出处，外键闭合，幂等键 `(identity_id, business_type, request_id)` 与 ADR-003 一致，`request_hash`、流水角色、CHECK 约束、建表顺序均正确。**但三处枚举值与 B/C 的类名基线冲突、外加 `customer` 表缺 `identity_id` 字段，共四项必须改**（状态机、业务类型与身份标识都是全局类名基准的一部分，D 的库表必须对齐）。另有几处命名规范自洽问题建议改。

## 必须改（与 B/C 基线冲突，不改会导致接口返回与库存值对不上）

### M-1 账户状态枚举：`ACTIVE` → `NORMAL`

| 来源 | 值 |
|---|---|
| D `account.status`（schema.sql 第 82、96 行；数据库设计 3.2.3） | `ACTIVE` / `FROZEN` / `CLOSED` |
| B design-class.puml（Account 注释） | `NORMAL` / `FROZEN` / `CLOSED` |
| C 模块设计 4.1（`payer.getStatus() != NORMAL`） | `NORMAL` / `FROZEN` / `CLOSED` |

D 用 `ACTIVE`，B/C 用 `NORMAL`。C 的 `checkOutgoing` 代码直接判 `!= NORMAL`，落库若存 `ACTIVE` 会全部误判为异常。**统一为 `NORMAL` / `FROZEN` / `CLOSED`**，改 schema.sql 的 CHECK 约束与默认值、数据库设计 3.2.3。

### M-2 交易状态枚举：缺 `RECOVERING`，且 `ACCEPTED`/`SUCCESS`/`UNKNOWN` 命名与 B/C 不一致

| 来源 | 值 |
|---|---|
| D `transaction.status`（schema.sql 第 136、156 行） | `ACCEPTED` / `PROCESSING` / `SUCCESS` / `FAILED` / `REJECTED` / `UNKNOWN`（6 态） |
| B/C `TransactionStatus`（design-class.puml、C 模块设计 5.1） | `RECEIVED` / `REJECTED` / `PROCESSING` / `PENDING` / `SUCCEEDED` / `RECOVERING` / `FAILED`（7 态） |

三处冲突加一处缺失：

1. 受理初始态：D `ACCEPTED` → B/C `RECEIVED`（B 的图 2-4：`Transaction(RECEIVED)`）。
2. 成功态：D `SUCCESS` → B/C `SUCCEEDED`（C 5.1 状态机、ADR-003 验证方式）。
3. 待确认态：D `UNKNOWN` → B/C `PENDING`（BR-16/17、UC-TR-08 核对待确认）。
4. **缺 `RECOVERING`（恢复中）**：C 的状态机核心状态——释放失败时 `markRecovering()`（4.1），UC-TR-09 重试资金恢复针对 `RECOVERING` 交易。D 漏掉它会导致跨行/取款失败恢复场景无法落库。

**统一为 B/C 的 7 态**：`RECEIVED` / `REJECTED` / `PROCESSING` / `PENDING` / `SUCCEEDED` / `RECOVERING` / `FAILED`。改 schema.sql 的 CHECK 约束与默认值（默认 `RECEIVED`）、数据库设计 3.2.5。

### M-3 业务类型枚举：`WITHDRAW`/`TRANSFER_INTERNAL`/`TRANSFER_EXTERNAL`/`PAYMENT` 与 C/E 不一致

| 来源 | 值 |
|---|---|
| D `business_type`（schema.sql 第 130、155 行） | `DEPOSIT` / `WITHDRAW` / `TRANSFER_INTERNAL` / `TRANSFER_EXTERNAL` / `PAYMENT` |
| C ADR-003 / 模块设计 3.1、E 接口清单 2.4 | `DEPOSIT` / `WITHDRAWAL` / `INTERNAL_TRANSFER` / `EXTERNAL_TRANSFER` / `ACCOUNT_OPEN` |

冲突：

1. 取款：D `WITHDRAW`（动词）→ C/E `WITHDRAWAL`（名词，与 `DEPOSIT` 词性一致）。
2. 本行转账：D `TRANSFER_INTERNAL` → C/E `INTERNAL_TRANSFER`（C 的 `claimOrLoad(identityId, INTERNAL_TRANSFER, requestId, …)` 逐字出现）。
3. 跨行：D `TRANSFER_EXTERNAL` → C/E `EXTERNAL_TRANSFER`。
4. D 多了 `PAYMENT`（无类模型出处，违反"每张表/每个值都要有出处"）——删除。
5. D 缺 `ACCOUNT_OPEN`（开户幂等，E 接口清单 2.4 节、UC-AC-01 携带 `requestId`）——补。

**统一为** `DEPOSIT` / `WITHDRAWAL` / `INTERNAL_TRANSFER` / `EXTERNAL_TRANSFER` / `ACCOUNT_OPEN`。改 schema.sql 的 CHECK 约束、数据库设计 3.2.5。

### M-4 `customer` 表缺 `identity_id` 字段，`transaction.identity_id` 失去来源

| 来源 | 内容 |
|---|---|
| B design-class.puml（Customer 类） | `- customerId: String`、`- identityId: String`、`- realNameStatus: RealNameStatus`（三个字段） |
| D `customer` 表（schema.sql 第 34—51 行） | 只有 `customer_id`、`name`、`phone`、`email`、`real_name_status`、`status`，**无 `identity_id`** |
| D `transaction.identity_id`（schema.sql 第 129 行） | `VARCHAR(64)`，幂等键首列（BR-11/12） |

`transaction.identity_id` 是幂等键 `(identityId, businessType, requestId)` 的首维，必须能追溯到某张表的主键或唯一键。D 的 `customer` 没有该列，`credential` 也没有；且 `transaction.identity_id` 是 `VARCHAR(64)`、`customer.customer_id` 是 `VARCHAR(32)`，宽度不同，不能等同。结果：受理交易时写入的 `identity_id` 无处可查，无法做"同一身份"的外键校验。

**补 `customer.identity_id VARCHAR(64) NOT NULL` + 唯一键 `uk_customer_identity_id`**（与 B 的设计类一致），或明确 `identity_id = customer_id` 并统一宽度。E 接口清单的注册/登录/幂等键均以 B 的 `identityId` 为准，无需改；D 需补字段。

## 建议改（D 内部命名规范不自洽，不影响接口但对不上 D 自己定的规则）

### S-1 枚举存法：`customer`/`credential` 用 TINYINT，与 D 3.1.1 的"枚举存 VARCHAR 大写英文常量"矛盾

D 在 3.1.1 命名规范写"枚举值存 `VARCHAR` 大写英文常量，不用魔法数字"，`account.status`、`transaction.status` 也确实用了 VARCHAR。但 `customer.real_name_status`（TINYINT 0/1/2）、`customer.status`（TINYINT 1/2/3）、`credential.credential_type`（TINYINT 1/2/3）、`credential.status`（TINYINT 1/2/3）、`risk_rule.enabled`（TINYINT 0/1）却用了数字。建议统一：要么全 VARCHAR 英文常量，要么在 3.1.1 写明"二元/小范围状态可用 TINYINT 并配注释"。当前是 D 自身规则与实现不一致。

### S-2 `customer.status` 的"冻结"语义待确认

BR-03 的冻结是**账户**状态，不是客户状态。D 给 `customer.status` 设了 `2=冻结`，但需求书没有"冻结客户"的用例（只有冻结账户 UC-AC-05）。建议确认客户是否需要冻结状态；若不需要，客户状态简化为 `正常`/`注销` 即可。

### S-3 `transaction` 表双写字段写权限未在表 2-3 标注

E 接口清单 1.2 节要求 `transaction` 表按字段划分写权限（受理字段由 transaction-service 写、资金推进字段由 account-service 写）。D 的表 2-3 列出了全部字段，但没有标注"谁写"。建议在 3.2.5 给每个字段补一列"写入方"，落实 Q-2（接口清单待确认事项）。

## 已通过核对（无需改）

| 项 | 核对结果 |
|---|---|
| 外键闭合 | `credential/account → customer.customer_id`、`account_status_log/transaction → account.account_id`、`transaction_flow/transfer_order/risk_event → transaction.trade_no`、`risk_event → risk_rule.rule_id`，全部闭合；`audit_log.trade_no` 故意不建外键且有理由 |
| 幂等唯一键 | `uk_transaction_request (identity_id, business_type, request_id)` 与 ADR-003、E 接口清单 2.4 一致；`request_hash CHAR(64)` 配套 |
| 流水角色 | `TRANSFER_OUT`/`TRANSFER_IN`/`DEPOSIT_IN`/`WITHDRAW_OUT` 覆盖四种实际资金事件；`uk_transaction_flow_role (trade_no, account_id, entry_role)` 防重复记账 |
| 拒绝不写流水 | 3.2.9 说明拒绝只写 `risk_event` 不写 `transaction_flow`（BR-19） |
| 可用余额不落库 | `account` 不存 A，按 `B-R` 计算（3.1.4，BR-04） |
| CHECK 约束 | `transfer_order` 的本行/跨行条件约束、`risk_rule` 的 `LIMIT_POLICY`/`ACCOUNT_STATUS` 形状约束都正确 |
| 建表顺序 | 按外键依赖逆序删表、正序建表，可重复执行 |
| 表数量 | 10 张，每张有类模型出处，`risk_rule_customer` 等无出处表已删除 |
