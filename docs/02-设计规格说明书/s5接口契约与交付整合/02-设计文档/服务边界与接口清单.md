## 1 服务边界与数据所有权

### 1.1 服务清单与职责边界

服务名取自图 2-1，`transaction-service` 的端点同时服务存款、取款与转账（理由见第 7 节决策 D-1）。

| 服务 | 职责边界 | 拥有的数据（表） | 对外端点前缀 | 承载的表 2-1 设计类 |
|---|---|---|---|---|
| `gateway` | 统一入口：路由、会话校验（401）、限流。不做对象级授权（403 归各服务） | 无 | `/api/v1/*` | — |
| `user-service` | 注册、登录、会话管理、客户信息；身份与实名 | `customer`、`credential`（含会话） | `/api/v1/auth`、`/api/v1/customers` | Customer（实体归此上下文，类定义见表 2-1） |

| `risk-service` | 出账/入账限额规则求值、账户状态规则、风控事件留痕、规则配置 | `risk_rule`、`risk_event` | `/api/v1/risk` | RiskRule、RiskEvent（实体归此上下文）、RiskCheckService |

### 1.2 数据所有权与写入权限

依据 ADR-001 的决定：四个服务共用数据库实例，按数据职责限定写入权限。写入权限划分如下（表 2-3 落库时由 D 逐表落实）：

| 表 | 主写服务 | 写入范围 | 其他服务 |
|---|---|---|---|
| `customer`、`credential` | user-service | 全部字段 | 只读 |
| `account` | account-service | 全部字段（余额、状态、个人限额、版本） | 其他服务只读，且只能经 account-service 的接口读 |
| `fund_entry` | account-service | 只追加，不修改不删除（BR-19） | 只读 |
| `account_status_log` | account-service | 冻结/解冻/注销留痕 | 只读 |
| `transaction` | transaction-service（受理字段）+ account-service（资金推进字段） | 受理字段：`trade_no`、`identity_id`、`business_type`、`request_id`、`request_hash`、`account_id`、`amount`、`currency`、`created_at` 由受理方（transaction-service）写入；资金推进字段：`status`、`accepted_at`、`completed_at`、`channel_evidence_id`、`last_channel_result`、`last_checked_at`、`failure_reason` 由 account-service 在记账事务内更新（ADR-002：状态与余额同一本地事务提交） | risk-service 只读 |
| `transfer_order` | transaction-service | 受理与清算状态 | account-service 只读 |
| `risk_rule`、`risk_event` | risk-service | 全部字段 | 只读 |
| `audit_log` | 各服务经公共审计组件写入 | 操作者、时间、对象、动作、原因、结果 | 由 D 统一设计（表 2-3） |

`transaction` 是唯一的共写表。双写有依据：ADR-002 已决定"账户服务在主库事务内写入预留、双方余额、流水和幂等结果"，交易状态推进必须与资金写入同事务（BR-15/19），否则会出现"余额已动但状态未更新"。受理与推进按字段划分，D5 对齐会确认后写入表 2-3 的字段说明。

## 2 统一接口约定

### 2.1 通用规则

1. 风格：REST over HTTP/1.1，JSON（UTF-8），路径前缀 `/api/v1/`；服务间内部接口前缀 `/internal/v1/`，不经 gateway。
2. 金额：字符串形式，两位小数（`"100.00"`），不用浮点数；服务端以 `Decimal`/`BigDecimal` 处理（BR-01）。
3. 时间：ISO-8601，东八区（`2026-10-27T16:30:00+08:00`）。
4. 分页：`page`（从 1 起）+ `pageSize`（默认 20，最大 100），响应用 `data.items` + `data.total`。
5. 所有写操作（POST）必须携带 `requestId`；查询（GET）不携带（见 2.4）。

### 2.2 统一响应体

与仓库 `backend/README.md` 的既定约定一致：

```json
{
  "code": "SUCCEEDED",
  "message": "本行转账已成功",
  "data": {
    "tradeNo": "TRD20261027000001",
    "status": "SUCCEEDED"
  },
  "traceId": "c0a80101-..."
}
```

| 字段 | 说明 |
|---|---|
| `code` | 业务状态码。资金类接口成功/处理中/失败用 `SUCCEEDED`/`PROCESSING`/`PENDING`/`RECOVERING`/`FAILED`（与 C 的状态机一致）；错误时为第 2.3 节错误码 |
| `message` | 面向用户的可解释反馈（NFR-06），不泄露他人信息（BR-20） |
| `data` | 业务数据。资金受理类接口必含 `tradeNo` 与当前 `status`；`REJECTED` 技术拒绝时 `tradeNo` 可空（B 的口径） |
| `traceId` | 全链路追踪标识，进入日志与 `audit_log`（NFR-03/10） |

HTTP 状态码与 `code` 并用：HTTP 表达传输层语义，`code` 表达业务语义。两者映射见错误码表。

### 2.4 `requestId` 幂等约定（BR-11/12，与 ADR-003 一致）

1. **生成**：前端生成 UUID，随每个写请求提交；同一次用户操作的重试必须复用同一 `requestId`。
2. **幂等键**：`(identityId, businessType, requestId)` 三元组，落 `transaction` 表唯一索引 `UK(identity_id, business_type, request_id)`。`businessType` 取 `DEPOSIT` / `WITHDRAWAL` / `INTERNAL_TRANSFER` / `EXTERNAL_TRANSFER` / `ACCOUNT_OPEN`。
3. **内容指纹**：`requestHash` = 规范化请求内容（字段按固定顺序、金额两位小数字符串、空值约定）的 SHA-256。同键同内容返回原交易**当前状态**快照（不缓存"处理中"）；同键异内容返回 409 `REQUEST_CONFLICT`。
4. **顺序**：先鉴权（401/403），后查幂等。命中 `requestId` 也不能绕过对象权限（B 的风险 1）。
5. **认领**：`IdempotencyService.claimOrLoad` 原子持久认领，禁止"先查再插"；并发冲突由唯一索引兜底，捕获后回查并有有限重试（ADR-003 验证方式 3）。
6. **二次幂等**：账户入账、扣账、占用、释放各自再按 `tradeNo` 幂等（条件更新），不靠交易表唯一键包办。
7. **终态不可重开**：`SUCCEEDED`/`FAILED`/`REJECTED` 后同三元组只返回原结果；新业务用新 `requestId`。
8. **保留期**：幂等记录在课程演示周期内不删除；数据量增大后归档而非清理（ADR-003 后果）。

### 2.5 服务间内部调用约定

1. **认证**：内部接口用服务身份（内部令牌）调用，不经 gateway；模拟渠道回执以约定的来源验证机制核对（B：回执须校验来源与关联；具体签名机制为实验三实现契约）。
2. **超时语义**：内部调用超时≠失败。资金命令超时后按 `tradeNo` 查询 account-service 当前状态，再决定继续、恢复或等待；禁止盲目重发资金命令（ADR-002）。
3. **重试**：只有幂等命令（按 `tradeNo` 条件更新）可重试；重试次数有限并记录。
4. **资金命令边界**：transaction-service 只发命令（`reserve`/`postInternalTransfer`/`releaseReservation`/`completeDeposit`/`recordFailure`），account-service 在本地事务内执行并返回 `PostingOutcome`；命令模型即图 2-13 的防腐层。
