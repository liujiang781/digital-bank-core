## ADR-004：前端技术栈

- **状态**：已接受（决策者 E；若 D5 对齐会确认多数组员更熟悉其他框架，按同格式重写本条并同步 `frontend/README.md`）
- **日期**：2026-10-27
- **决策者**：E
- **关联**：ADR-001（架构风格）、任务清单 3.5、`frontend/README.md`

### 背景

实验三需要实现前端原型：登录、账户列表/详情、余额展示（B/R/A）、存款与转账表单、交易与流水列表。任务清单为 ADR-004 设定的考量顺序是：**组员熟悉度 > 生态 > 新鲜度**，明确"不要为了用新技术让全组卡在环境上"。指导书实验环境允许 Vue.js / React / Angular 或 Bootstrap。仓库 `frontend/README.md` 已按 Vue 3 完成目录规划（`vite.config.js` 配 `/api` 代理到网关、`src/api/` 按模块拆分、统一拦截器处理错误码），但框架行标注"待定（备选 React）"，需要定稿。

### 候选方案

| 维度 | 方案 A：Vue 3 + Element Plus + Vite | 方案 B：React + Ant Design | 方案 C：服务端渲染模板（Thymeleaf） |
|---|---|---|---|
| 组员上手成本 | 低：国内课堂最常见组合，模板语法直观 | 中：JSX 与函数组件心智负担更高 | 最低：无独立前端工程 |
| 与仓库现状 | `frontend/README.md` 已按 Vue 3 完成目录与约定规划 | 需重写目录规划与全部约定 | 需改后端服务承担页面渲染 |
| 组件生态 | Element Plus 的表单、表格、弹窗、消息覆盖银行界面全部场景 | Ant Design 同样覆盖 | 需手写全部交互 |
| 与架构的匹配 | 前后端分离，经 gateway 调 `/api/v1/`，独立部署展示 | 同左 | 服务端渲染与"四个独立服务 + 网关"的部署形态不匹配 |
| 资金界面特殊要求 | Axios 拦截器统一处理错误码与 401 跳转；表单校验金额两位小数；提交按钮 loading + 二次确认（转账） | 同左可实现 | 拦截器逻辑散落在后端 |
| 两周工期可行性 | 高 | 中（叠加熟悉度风险） | 高但牺牲前端独立性 |

### 决策

采用**方案 A：Vue 3（`<script setup>`）+ Vite + Element Plus + Vue Router + Pinia + Axios**。配套约定沿用 `frontend/README.md`：接口统一走 `src/api/`，组件不写裸调用；金额展示 `¥1,234.56` 两位小数，不用浮点运算；所有提交按钮有 loading 态 + 二次确认；错误提示直接用后端统一响应体的 `message`。

### 理由

选 A 的直接依据是熟悉度优先原则与仓库现状：Vue 3 是国内课程项目最常见的前端组合，组员平均上手成本最低；`frontend/README.md` 已经完成了 Vue 3 的目录规划、代理配置和开发约定，选它能最大化复用既有工作。Element Plus 对表单、表格、弹窗的覆盖，正好匹配本项目以"账户卡片 + 交易表格 + 转账表单"为主的界面形态。

不选 B：React + Ant Design 生态同样成熟，但组内没有既定的 React 规划或强偏好，切换意味着重写目录约定、放弃已完成的代理与拦截器设计，收益为零。

不选 C：Thymeleaf 方案把页面渲染压回后端，与 ADR-001 的四服务 + 网关架构冲突——页面逻辑要跨 user/account/transaction 三个服务聚合，等于在服务端重新实现一层展示编排；而且实验环境明确鼓励现代框架，C 会损失前后端分离带来的独立部署展示点。

### 后果

- **正面**：
  - 前端独立工程，经 gateway 访问 `/api/v1/`，与图 2-2 部署形态一致；
  - Axios 拦截器统一映射第 2.3 节错误码注册表与统一响应体，错误提示口径唯一；
  - 目录规划已就绪，实验三可直接开工。
- **负面 / 需要承担的成本**：
  - 需要 Node.js 工具链（Vite 构建），组员需统一 Node 版本；
  - 前后端联调依赖接口契约稳定，本清单（`服务边界与接口清单.md`）就是两端的合同，改接口必须先改清单；
  - Element Plus 版本升级可能有破坏性变更，实验周期内锁定版本；
  - 不做 SSR/SEO，纯管理端场景无此需求，属于主动放弃而非遗漏。

## ADR-005：数据库与缓存选型

- **状态**：已接受（决策者 E）
- **日期**：2026-10-27
- **决策者**：E
- **关联**：ADR-001/002/003、图 2-2（Redis 可选节点）、D 的表 2-3 与 `schema.sql`

### 背景

资金业务要求：金额精确（BR-01，两位小数）、余额不变式（BR-04：A=B−R、B≥0、0≤R≤B）、双方账户同事务提交（BR-15）、幂等唯一约束（BR-11/12，ADR-003 已依赖 `UK(identity_id, business_type, request_id)`）。图 2-2 把 Redis 画成条件节点，是否启用由本 ADR 决定。D 的表 2-3 与 `schema.sql` 需要一个确定的数据库目标（任务清单要求 MySQL 8 一次执行通过）。

### 候选方案

| 维度 | 方案 A：MySQL 8（InnoDB），不引入 Redis | 方案 B：MongoDB + Redis | 方案 C：MySQL 8 + Redis 缓存 |
|---|---|---|---|
| 事务与一致性 | ACID 完整，行锁 + 固定顺序加锁支撑 ADR-002 | 多文档事务有使用限制，金额场景验证成本高 | ACID 同 A |
| 金额精度 | `DECIMAL(18,2)` 精确 | 无内建精确小数类型，需自行封装 | 同 A |
| 幂等支撑 | 唯一索引天然支撑 ADR-003 | 需要额外唯一性方案 | 同 A，但 ADR-003 已论证不需要 Redis 锁 |
| 读性能 | 并发 10 人（NFR-04）单库可满足，可读从库 | 高写入吞吐 | 增加缓存层，P95≤2s 场景收益有限 |
| 运维与调试成本 | 最低，单实例可验证全流程 | 两个新增组件 | 新增一个组件 |
| 组员熟悉度 | 高（课程主流） | 低 | 中 |
| 两周工期 | 可行 | 紧张 | 可行但属过度设计 |

### 决策

采用**方案 A：MySQL 8（InnoDB、`utf8mb4`、金额 `DECIMAL(18,2)`、时间 `DATETIME`），不引入 Redis**。配套约定：

1. 部署形态按图 2-2：主库承担全部资金写入与校验读取；从库异步复制，仅用于容忍延迟的查询；资金判断与结果确认一律读主库（ADR-002 后果）。
2. 图 2-2 的 Redis 节点标注"不启用（ADR-005）"或删除（组长执行，见接口清单 Q-3）。
3. 查询压力的兜底路径：若实验四压测发现余额查询超 P95≤2s，先读从库，再评估缓存；在本迭代内不做预优化。
4. D 的 `schema.sql` 目标定为 MySQL 8，`id` 代理主键 + 业务唯一键（`trade_no`、`account_id` 等）按 C 交接清单落库。

### 理由

选 A 是因为项目的硬约束全部指向关系型数据库：ADR-002 的资金原子性靠 InnoDB 本地事务，ADR-003 的幂等靠唯一索引，两者都不需要额外组件。MongoDB 在多文档事务与精确小数上都要额外验证，对两周工期是纯风险。

不引入 Redis 的依据是"无明确需求即不引入"：本迭代没有任何一条需求需要缓存。余额查询的量级由 NFR-04 给定（并发 10 人、P95≤2s），单库加从库足够；幂等键在 ADR-003 已明确用数据库唯一约束而非 Redis 锁；日额度占用（BR-07）是资金一致性运算，放进缓存反而引入新的不一致。此时引入 Redis 只会增加部署、调试和答辩解释成本，属于任务清单点名的过度设计。

### 后果

- **正面**：
  - 零新增组件，实验三建库、实验四压测都用同一套环境；
  - 一致性验证路径单一：资金正确性全部由数据库约束与本地事务保证，可证明、可复现；
  - 与 ADR-003 形成闭环：幂等、一致性、精度都有落点。
- **负面 / 需要承担的成本**：
  - 所有并发压力集中在 MySQL 主库；固定顺序加锁（C 的 `postInternalTransfer`）在高并发下有锁竞争，实验四压测需覆盖双向转账场景；
  - 从库异步复制有延迟，读从库的接口必须容忍读到旧数据（余额查询的兜底路径需在实验四验证）；
  - 若未来真实并发远超 10 人量级，需要重新评估缓存与分库——本决策只覆盖课程迭代范围；
  - 图 2-2 的 Redis 节点需要组长同步修改，保持图文一致（风险 R-04 同类问题）。
