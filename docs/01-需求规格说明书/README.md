# 实验一 · 需求规格说明书

**目标**：调研分析、建立用户故事地图、确定系统需求，用 UML 建立软件问题模型（分析模型）。

## 写作清单

### 1. 项目概述与迭代规划

- [ ] `1.1 项目背景与目标`：核心问题、目标用户、价值（400-600 字，不要写成产品吹嘘）
- [ ] `1.2 迭代规划`：几个 Sprint、每轮周期与核心目标、简化版产品 Backlog 或用户故事地图截图
  - 素材来源：[BACKLOG.md](../../BACKLOG.md)

### 2. 系统用例分析

- [ ] `2.1 角色分析` → **表 1-1 角色列表**（编号 / 角色名 / 所属部门 / 简要描述）
  - 本系统角色建议：客户、柜员（可选）、风控管理员、系统管理员
- [ ] `2.2 用例分析` → **表 1-2 用例列表**（编号 / 用例名 / 角色 / 优先级 / 描述）
  - 只列基本用例，不含精化后的扩展用例
- [ ] `2.3 用例建模`：按功能模块画**用例图** + 用例表 + 复杂事件流的**活动图**
  - 必画活动图：存款、取款、跨行转账、风控拦截
- [ ] `2.4 数据建模`：名词短语法 + CRC 分析，得出**分析类模型（域模型）**
  - 重点实体：客户 Customer、账户 Account、交易流水 Transaction、风控规则 RiskRule

### 3. 非功能需求

- [ ] 性能（并发、响应时间）、可靠性（资金一致性）、安全性（权限、脱敏）、可用性、可维护性
- [ ] 每条非功能需求尽量给出**可度量指标**，如"单笔转账 P95 响应 ≤ 500ms"

## 建议图清单

| 图        | 说明              |
| -------- | --------------- |
| 用户故事地图   | 按"用户活动→任务→故事"分层 |
| 用例图（总图）  | 角色与用例关系         |
| 用例图（按模块） | 每个功能模块一张        |
| 活动图      | 存款/取款/转账/风控     |
| 域模型类图    | 只到概念层，不含方法实现细节  |

## 常见扣分点

- 用例列表与用例图对不上（图里有、表里没有）
- 活动图只画 happy path，没有余额不足、账户冻结、风控拦截等异常分支
- 角色写成了"用户"，没区分客户与管理员
- 域模型里混入了数据库字段（`varchar(50)` 这种），概念模型不该出现实现细节
