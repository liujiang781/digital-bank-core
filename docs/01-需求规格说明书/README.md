# 实验一 · 需求规格说明书

**目标**：调研分析、建立用户故事地图、确定系统需求，用 UML 建立软件问题模型（分析模型）。

## 写作清单

### 1. 项目概述与迭代规划

- [ ] `1.1 项目背景与目标`：

  本项目选择选题一，开发一个数字银行核心业务模拟系统。随着银行业务逐步转向线上，客户希望随时查看账户信息并办理常见交易；管理人员则需要掌握账户状态，识别和处理异常交易。本项目以这些基本需求为背景，通过课程原型梳理数字银行业务流程，并验证账户资金变动的正确性和可追溯性。

  系统面向客户、系统管理员和风控管理员。客户可以注册、登录、开立活期账户、查询余额与交易流水，并办理存款、取款、本行转账和模拟跨行转账。管理员可以冻结或解冻账户，查看风控拦截记录。系统在交易过程中校验账户状态、可用余额和交易限额；重复提交同一请求时不得重复扣款或入账。每笔实际资金变动均生成可追溯的流水，本行转账的转出与转入必须同时成功或同时失败。

  本项目重点完成需求分析、系统建模和可运行原型，跨行清算仅通过模拟流程展示处理状态及结果。系统不连接真实银行或支付机构，也不处理真实资金、利息、贷款和理财业务。通过明确业务范围、异常处理规则和迭代优先级，小组将在后续实验中逐步完成设计、实现与测试。
- [ ] `1.2 迭代规划`：

  项目按需求分析、系统设计、原型实现和测试部署逐步推进。每轮结束时检查对应交付物，并将发现的需求问题反馈到 Backlog 和相关模型中。

  | 阶段            | 预计周期     | 核心目标              | 主要交付物                             |
  | ------------- | -------- | ----------------- | --------------------------------- |
  | Sprint 0      | 第 1 周    | 确定选题、协作方式与初始需求    | 项目说明、初始 Backlog、需求问题清单            |
  | Sprint 1（实验一） | 第 2—3 周  | 确认业务范围和优先级，完成需求分析 | 需求规格说明书、用户故事地图、用例模型、活动图、CRC 与领域模型 |
  | Sprint 2（实验二） | 第 4—5 周  | 比较架构方案并完成系统设计     | 架构决策、包图、部署图、序列图、数据设计              |
  | Sprint 3（实验三） | 第 6—8 周  | 构建可运行原型，优先打通存款流程  | 界面与核心业务代码、存款端到端演示、实现说明            |
  | Sprint 4（实验四） | 第 9—10 周 | 验证功能与异常规则，整理部署方案  | 测试用例和记录、部署方案、实验报告定稿               |

  优先级采用现有 Backlog 的约定：P0 为必须完成的核心能力，包括开户登录、账户查询与冻结、存款、取款、本行转账、流水、幂等和单笔限额；其中存款端到端流程是原型阶段的必验内容。P1 包括模拟跨行转账、日累计限额等增强功能；P2 为工期允许时完成的高频交易识别。实验一仍需分析跨行转账等重要 P1 业务，为后续实现提供依据。

### 2. 系统用例分析

- [ ] `2.1 角色分析` → **表 1-1 角色列表**（编号 / 角色名 / 所属部门 / 简要描述）
  - 本系统角色建议：客户、柜员（可选）、风控管理员、系统管理员
- [ ] `2.2 用例分析` → **表 1-2 用例列表**（编号 / 用例名 / 角色 / 优先级 / 描述）

  - 重点实体：客户 Customer、账户 Account、交易流水 Transaction、风控规则 RiskRule

### 3. 非功能需求

- [ ] 性能（并发、响应时间）、可靠性（资金一致性）、安全性（权限、脱敏）、可用性、可维护性

## 常见扣分点

- 用例列表与用例图对不上（图里有、表里没有）
- 活动图只画 happy path，没有余额不足、账户冻结、风控拦截等异常分支
- 角色写成了"用户"，没区分客户与管理员
- 域模型里混入了数据库字段（`varchar(50)` 这种），概念模型不该出现实现细节
