# 实验一需求确认讨论纪要

> 本文由 S1 按 S1—S5 的既定职责模拟讨论并形成可执行的需求基线。S1—S5 的意见是角色代拟，不代表成员实际发言；会议日期、真实参会人和签字不在此虚构。小组实际采用时由成员复核并确认。

## 一、讨论议题与各角色意见

| 角色 | 模拟讨论意见 | 形成的决定 |
|---|---|---|
| S1（组长，范围与优先级） | 课程项目应聚焦数字银行核心业务，先保证实验一模型完整，并为后续可运行原型划定验收线。 | 采用第二区分的范围，按现有 Backlog 的 P0/P1/P2 排序，不把实验二的架构选型提前写成需求结论。 |
| S2（交易用例） | 存款、取款、本行转账、跨行转账都要有成功与失败路径；冻结、余额不足和重复提交必须能在用例中验证。 | 采用第三节的交易规则；跨行仅模拟清算，失败时释放预留资金。 |
| S3（角色、风控与非功能需求） | 冻结应禁止出账；限额应作用于可能造成资金流出的交易。原型需要确定可测试的演示阈值。 | 冻结账户可入账、不可出账；取款与转账在出账前校验单笔和日累计限额。 |
| S4（故事地图） | 故事地图应按客户活动组织，管理员操作单独展示，优先级要与 Backlog 相同。 | 按“开户登录→管理账户→办理交易→查询结果”组织客户故事，另列管理员冻结与风控查询故事。 |
| S5（候选类、CRC 与领域模型） | 账户、交易流水和跨行转账状态应有清晰区别，才能说明失败、幂等及追溯规则。 | 分析模型至少覆盖 Customer、Account、Transaction、TransferOrder、RiskRule；不在概念模型写数据库字段或技术实现。 |

## 二、业务边界

### 纳入范围

1. 客户注册、实名信息、登录认证；活期账户开立、账户列表、余额和状态查询。
2. 管理员冻结与解冻账户；客户办理存款、取款、本行转账和模拟跨行转账。
3. 交易流水记录与查询、对账查询；单笔限额、日累计限额和异常交易拦截。
4. 支持上述业务所需的基础权限控制、输入校验和敏感信息脱敏。

### 排除范围

不接入人民银行支付系统、银联或真实银行接口；不进行真实资金清算；不实现利息、贷款、理财和生产级安全合规认证。跨行收款行与清算结果都由系统模拟。

## 三、业务规则决议

| 编号 | 决议 | 用例与验收要点 |
|---|---|---|
| BR-01 | 账户冻结后禁止取款、本行转出和跨行转出；允许存款等入账。解冻后恢复出账资格。 | 冻结账户提交出账请求时直接拒绝，余额不变，提示冻结原因；入账成功仍留下流水。 |
| BR-02 | 取款和转账的金额必须大于零，且不得超过可用余额。 | 金额无效或余额不足时拒绝出账，账户余额不变，并给出明确原因。 |
| BR-03 | 每个交易请求带唯一请求标识；同一标识和相同内容重复提交只处理一次并返回原结果。同一标识对应不同内容时拒绝。 | 重复点击或网络重试不能产生第二次扣款、入账或资金流水。 |
| BR-04 | 每次实际资金变动都生成可追溯的交易流水。已产生的流水不得修改或删除；需要纠错时追加冲正流水。 | 流水含唯一编号、账户、交易类型、金额、时间、状态和关联交易编号；可按时间、金额和类型查询。失败但未造成资金变动的请求保留处理/拦截记录，不伪造资金流水。 |
| BR-05 | 取款、本行转出和跨行转出在出账前接受风控校验；存款不适用出账限额。单笔上限暂定 5 万元，同一账户当日出账累计上限暂定 10 万元，均为课程模拟参数。 | 超限时拒绝并记录拦截事件，资金不变；阈值可配置，不宣称是真实银行规则。单笔校验列为 P0，日累计校验列为 P1。 |
| BR-06 | 本行转账的付款扣减与收款增加必须同时成功或同时失败。 | 任一账户校验失败时双方余额均不变；成功时双方流水可以用同一交易编号关联。 |
| BR-07 | 跨行转账仅模拟“处理中→成功/失败”。受理时预留付款账户可用资金；成功时完成扣减，失败时释放预留资金。 | 处理中不可重复动用该笔资金；最终失败不会造成资金损失；状态变化和最终资金变动可追溯。 |
| BR-08 | 仅客户本人可以查看自己的账户和交易；冻结/解冻及风控拦截记录由有权限的管理员处理。 | 越权访问被拒绝；展示敏感身份信息时作必要脱敏。 |

## 四、范围和优先级决议

优先级与现有 `BACKLOG.md` 保持一致。P0 是课程原型的必须项，P1 应完成，P2 在时间允许时完成；P1/P2 仍属于分析范围，实验一需要描述其需求和关键流程。

| 优先级 | 用户故事或交付项 | 决议 |
|---|---|---|
| P0 | US-01、US-02、US-10—US-13、US-20—US-22、US-24、US-25、US-30、US-40—US-43；EN-02、EN-03 | 开户登录、账户查询与冻结、存取款和本行转账、流水与幂等、单笔限额及对应页面；完成故事地图、用例与领域模型。存款 US-20 是后续原型的必验流程。 |
| P1 | US-03、US-04、US-23、US-31、US-33 | 资料维护、客户管理、模拟跨行转账、日累计限额和拦截记录查询。对账查询作为流水查询的延伸，不增加真实清算范围。 |
| P2 | US-32 | 高频交易可疑标记，工期不足时可保留分析说明而不实现。 |

本次特别校正：余额与状态查询 US-11、账户列表 US-12、冻结/解冻 US-13 均为 **P0**，不能在纪要中降为 P1。跨行转账 US-23 为 **P1**，但实验一仍需分析其活动流程。

## 五、迭代与实验一交付

| 阶段 | 核心目标 | 本次需求基线的作用 |
|---|---|---|
| Sprint 0 | 立项、仓库和需求调研 | 整理初始 Backlog 与待讨论问题。 |
| Sprint 1（实验一） | 需求分析与迭代规划 | 完成范围/优先级、用户故事地图、角色及用例列表、用例图、存款/取款/跨行转账/风控拦截活动图、CRC 与领域模型、可度量非功能需求。 |
| Sprint 2（实验二） | 架构与详细设计 | 根据确认的需求比较架构方案，设计交互、部署和数据结构。 |
| Sprint 3（实验三） | 可运行原型 | 优先打通 US-20 存款端到端流程，再实现其他 P0 业务与可行的 P1。 |
| Sprint 4（实验四） | 测试与部署 | 用成功及异常场景验证规则，完成测试记录和部署方案。 |

## 六、主责、复核与交接

| 产出 | 主责 | 复核 | 交接要求 |
|---|---|---|---|
| 范围、优先级、迭代规划与本纪要 | S1 | S2 | 检查编号、P0/P1/P2 与 Backlog 一致。 |
| 交易用例及存款、取款、转账活动图 | S2 | S3 | 覆盖冻结、余额不足、超限、重复请求和跨行失败分支。 |
| 角色、风控与非功能需求 | S3 | S4 | 区分客户和管理员；性能、安全与可靠性给出可验证指标。 |
| 用户故事地图 | S4 | S5 | 按用户活动→任务→故事分层，标注优先级。 |
| 候选类、CRC 和领域模型 | S5 | S1 | 说明客户、账户、交易、转账订单及风控规则的职责与关系。 |

业务规则先按第三节统一，再由主责成员整理到各自交付物，交另一名成员复核。若后续更改规则或优先级，S1 负责提醒相关成员同步修订故事地图、用例表、UML 图和领域模型。
