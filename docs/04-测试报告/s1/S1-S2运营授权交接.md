# S1 → S2 运营角色与账户范围授权交接

> 2026-11-18 更新：已增加在线角色/账户范围管理和授权版本失效机制，数据库记录优先于本文件的静态清单；部署时需执行 S1 增量 SQL。新增接口与迁移说明见 [用户管理接口交接](S1-用户管理接口交接.md)。下文保留 2026-11-17 的原始验证记录。

日期：2026-11-17。范围：实验四账户冻结、解冻及越权测试所需的登录授权链路。

## 1. 已实现的交接契约

1. `user-service` 从服务端 `auth.staff.grants` 读取身份对应的角色和账户授权范围。
2. 登录签发的会话包含角色和范围；内部核验重新检查凭据状态、密码及授权是否仍与会话一致。
3. 网关和账户服务分别校验 Bearer 令牌；账户服务的认证过滤器提供公共 `SessionIdentity` Principal。
4. `AccountAccess` 将可信后台身份转换为 S2 自己的 `Actor`，普通客户仍按正常、已实名客户记录核验归属。
5. S2 同时校验角色和明确账户范围。没有授权记录时，两项均为空。

认证响应中的身份结构：登录响应位于 `data.customer`，`GET /api/v1/auth/me` 和内部会话核验位于 `data`。

```json
{
  "customerId": "STAFF-OPS-S2",
  "identityId": "ops-s2",
  "roles": ["OPERATIONS"],
  "accountScope": ["S2-ACCOUNT-A"]
}
```

| 身份 | 授权账户 | 冻结 | 解冻 |
|---|---|---|---|
| `OPERATIONS` | 在 `accountScope` 内 | 允许 | 允许，仍需满足 S2 的解除依据等业务校验 |
| `RISK` | 在 `accountScope` 内 | 允许 | 403 |
| 任意后台角色 | 范围外或范围为空 | 403 | 403 |
| 普通客户 | 即使是本人账户 | 403 | 403 |
| 未登录或已退出 | 任意账户 | 401 | 401 |

角色和范围来自服务端，不读取客户端 `X-Roles`、`X-User-Roles`、`X-Account-Scope` 等头。网关清除伪造身份头，直连账户服务同样不能利用这些头提权。不支持 `*` 通配范围或未定义的后台角色。旧会话 JSON 缺少授权字段时默认为空。

## 2. S2 如何独立复现授权测试

在工作区根目录使用 JDK 21，先按现有 Maven 设置打包全部模块，再运行：

```powershell
python 'digital-bank-core/backend/scripts/staff_auth_smoke.py' `
  --java 'E:/Java/jdk-21/bin/java.exe' `
  --h2-jar 'tools/maven-repository/com/h2database/h2/2.3.232/h2-2.3.232.jar' `
  --output 'digital-bank-core/docs/04-测试报告/s1/证据/2026-11-17/staff-auth-results.json'
```

脚本自动启动用户服务、账户服务和网关三个真实进程，使用随机空闲端口、随机密码和服务密钥。账户数据库为独立 H2（MySQL 兼容模式），包含账户 `S2-ACCOUNT-A`、`S2-ACCOUNT-B`。脚本不连接现有 MySQL，不改真实数据，结束时只停止自己启动的进程。

测试身份：普通客户 `smoke-customer`、运营 `ops-s2`、风控 `risk-s2`、无范围运营 `ops-no-scope`。运营及风控只获账户 A 权限，B 用于越权反例。密码在运行时生成，不写入证据，不提供固定弱密码。

覆盖真实登录、角色及范围核验、普通客户拒绝、无范围拒绝、范围外拒绝、伪造头拒绝、直连端口拒绝、运营/风控冻结、运营解冻、退出失效、余额不变及审计记录。脚本结束后测试令牌不可继续使用。

## 3. 使用现有 MySQL / 手动联调

示例配置为 `deploy/auth-staff.example.yml`。用户服务需要额外加载该文件，其他服务不加载授权清单。

```powershell
# 在用户服务所在终端设置；将路径和账户 ID 换为本机实际值。
$env:SPRING_CONFIG_ADDITIONAL_LOCATION = 'file:E:/exp/软件工程实验/digital-bank-core/deploy/auth-staff.example.yml'
$env:BANK_OPERATIONS_ACCOUNT_ID = '<真实存在的账户业务ID>'
```

示例中的三个身份为 `ops-s2`、`risk-s2`、`ops-no-scope`。角色、范围可由 S1 按实际身份修改。

**MySQL 凭据模式**：设置 `BANK_CREDENTIAL_STORE=mysql`，保持演示模式关闭。S4 为这些身份准备正常状态的 `customer` 和 `USERNAME` 类型的 `credential` 记录，密码使用 BCrypt 哈希；当前凭据查询仍基于这两张表，未新增独立员工表。`auth.staff.grants` 只授予已有身份权限，不创建凭据，也不绕过密码验证。数据库连接仍使用 `BANK_DB_URL`、`BANK_DB_USERNAME`、`BANK_DB_PASSWORD`。

**显式 demo 模式**：设置 `BANK_CREDENTIAL_STORE=demo`、`BANK_DEMO_ENABLED=true`，按原约定提供基础演示身份和 12—72 字节的 `BANK_DEMO_PASSWORD`。另外提供三个 12—72 字节密码环境变量：`BANK_OPERATIONS_PASSWORD`、`BANK_RISK_PASSWORD`、`BANK_NO_SCOPE_PASSWORD`。额外 demo 员工凭据仅在 demo 开启时生效。它们的 `customerId` 为联调标识，不自动插入数据库；普通客户业务仍要求存在匹配的已实名客户记录。

所有服务的 `BANK_INTERNAL_TOKEN` 必须一致且至少 32 字节。网关默认 8085，用户服务 8081，账户服务 8082。账户服务数据库及 S2 增量脚本按原部署说明配置。

授权配置从用户服务启动时读取。修改授权后重启用户服务，旧内存会话全部失效，必须重新登录。这里提供静态授权清单，未增加角色管理页面或在线授权接口。

## 4. 手动请求示例

先 `POST /api/v1/auth/login`，请求体为 `identityId` 和对应密码，取 `data.token`；后续设置 `Authorization: Bearer <token>`。

冻结：`POST /api/v1/accounts/{accountId}/freeze`。

```json
{"reason":"运营核查冻结","requestId":"721e6ec7-e171-420b-a457-26a59dca11b1"}
```

保存冻结响应 `data.restrictions` 中的所有 `restrictionId`。解冻：`POST /api/v1/accounts/{accountId}/unfreeze`。

```json
{
  "reason": "核查完成",
  "releaseEvidence": "全部限制的核查依据",
  "resolvedRestrictionIds": [1, 2],
  "requestId": "d7409bd6-b1e4-40b0-8d51-615367d6ffb9"
}
```

限制编号必须使用实际返回值，并覆盖全部当前有效限制；每个新操作使用独立 UUID。权限通过后仍可能因账户状态、缺少原因、解除依据不足等业务校验被拒绝，不能把这些拒绝当作授权失败。
