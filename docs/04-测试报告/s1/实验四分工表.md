## 二、当前范围与优先级

1. **优先完成**：认证/网关、账户与记账、存款闭环、幂等、风控，以及数据库与部署验证。现有测试可以复用，但必须在选定基线上重新执行并记录结果。
2. **本轮纳入**：取款、本行转账已有业务入口与相关页面，纳入本轮接口、页面及端到端测试；模拟跨行转账的后端编排与账户记账已入库，纳入后端接口、组件及跨服务联调测试。未实现或未联通的功能不填“通过”，也不以内部记账接口通过代替整条业务通过。
3. **前端联调**：当前 `frontend/` 已有 Vue 业务页面，需连接真实服务与数据库执行页面和端到端验证；跨行转账页面尚未开放，单独登记为前端范围缺口。页面已入库不表示联调通过，S5 按实际操作记录结果及阻塞原因。
4. **校正旧模板**：`测试用例清单.md` 中的 `TransferService.transfer()`、固定错误码、日累计金额、白名单及“跨行超时直接失败回滚”等均需对照当前需求基线与真实代码核对。超时应区分明确失败与结果未决，不能仅因超时就断言失败。
5. **部署如实描述**：现有 `deploy/docker-compose.dev.yml` 是依赖环境方案，不能据此声称已一键部署全部应用。允许采用“Compose 启动依赖 + 分步启动应用”的可复现方案，并明确实际部署拓扑。

## 四、统一记录与交付要求

- **基本路径法**：记录源文件、方法名、被测提交、控制流图、节点/边与 V(G) 计算过程、独立路径及对应输入。按真实控制流计算，不能照抄模板中的“4 个判断、复杂度 5”。
- **等价类划分法**：先列输入域的有效/无效等价类，再把用例关联到等价类；限额、金额精度等增加边界测试，期望依据写清楚。
- **表 4-1 组件测试记录**：编号、路径标识、输入、期望输出、实际输出、发现问题、结果、时间、测试人。
- **表 4-2 功能测试记录**：编号、功能名称、输入、期望输出、实际输出、发现问题、结果、时间、测试人。
- **证据**：补充运行命令或操作步骤、环境、数据库前后状态、日志/截图路径。结果只填实际执行情况；未执行用例写明阻塞原因。H2 或模拟依赖的通过不能替代真实 MySQL 与跨服务联调记录。
- **缺陷**：记录关联用例、重现步骤、严重程度、负责人、状态、修复提交和回归结果；外部 Issue 建立后补链接。
- **编号**：新增用例使用 `CT-S1-001`、`FT-S2-001`、`E2E-S5-001`、`DEP-S4-001` 等，避免多人冲突；保留原有编号的追溯关系。
- **统计**：总数 = 通过 + 失败 + 未执行；通过率明确按“通过数 / 已执行数”计算，已执行数为 0 时写“不适用”；另列执行率，不能把未执行隐藏掉。
- **退出条件**：计划内用例均有执行结果或经组内确认的未执行说明；阻断存款闭环、重复入账、资金不一致、越权等严重缺陷修复并回归；部署能复现；其余遗留问题逐项说明影响与处置。
- **协作**：各成员独立分支提交、交叉 Review，遵守 `CONTRIBUTING.md`；总结、互评和 AI 记录以真实工作与 Git 证据填写。
