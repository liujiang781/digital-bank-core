# 数字银行实验四部署方案

## 部署范围与拓扑

目标部署沿用实验二微服务设计：浏览器通过网关访问用户、账户、交易和风控服务，交易服务再调用账户和风控，业务数据写入 MySQL 主库。实验二的 Nginx、只读从库和 Redis 属于扩展设计；当前开发部署采用前端 Vite、五个后端进程与单 MySQL，不声称已建立 Nginx、主从复制或 Redis 会话持久化。当前 Compose 只提供 MySQL 和可选 Redis。

本轮已实际启动并验证 user-service 与 gateway 的认证链路，未执行完整 MySQL 部署。下列资金业务部署和恢复步骤需由 S4 在独立实验数据库验证后补记录。

## 环境与端口

| 组件 | 要求或默认端口 | 说明 |
| --- | --- | --- |
| JDK 与构建 | JDK 21，Maven | 本轮使用 21.0.7、3.9.11 |
| 前端 | Node.js 及 npm，5173 | npm ci 后 npm run dev；生产静态资源由 npm run build 生成 |
| user-service | 8081 | 登录、当前身份、会话验证与退出 |
| account-service | 8082 | 账户、余额、预留及原子记账 |
| transaction-service | 8083 | 存取款、转账、幂等与恢复 |
| risk-service | 8084 | 风控校验 |
| gateway | 8085 | 前端代理默认与此端口一致 |
| MySQL | 3306，Compose 镜像 8.0.36 | 仅在独立实验数据库导入数据 |
| Redis | 6379，可选 | 当前 S1 会话使用进程内存，Redis 不是已实现的会话存储 |

## 配置项

| 服务 | 环境变量 | 配置要求 |
| --- | --- | --- |
| 用户与网关及业务服务鉴权 | BANK_INTERNAL_TOKEN，USER_SERVICE_URL | 内部认证令牌至少 32 字符；使用同一认证服务地址 |
| MySQL 用户认证 | BANK_CREDENTIAL_STORE=mysql，BANK_DB_URL，BANK_DB_USERNAME，BANK_DB_PASSWORD | mysql 模式按 identityId 登录；BANK_DEMO_ENABLED=false |
| 账户服务 | ACCOUNT_DB_URL，ACCOUNT_DB_USER，ACCOUNT_DB_PASSWORD，ACCOUNT_INTERNAL_TOKEN | 数据库连接及账户内部记账令牌 |
| 交易服务 | TRANSACTION_DB_URL，TRANSACTION_DB_USER，TRANSACTION_DB_PASSWORD，TRANSACTION_INTERNAL_TOKEN | 数据库连接及内部访问令牌 |
| 风控服务 | RISK_DB_URL，RISK_DB_USER，RISK_DB_PASSWORD，RISK_INTERNAL_TOKEN | 数据库连接及风控内部令牌 |
| 交易依赖地址 | ACCOUNT_SERVICE_URL，RISK_SERVICE_URL | 默认 localhost:8082、localhost:8084 |
| 前端 | GATEWAY_URL | 可覆盖默认 http://localhost:8085 |
| JVM | JAVA_TOOL_OPTIONS | 可按机器资源设置 -Xms256m -Xmx512m；本轮未做容量验证 |

各服务在自己的终端配置数据库账号，避免一个进程的数据库变量误用于另一服务。BANK_INTERNAL_TOKEN 与账户/风控业务内部令牌用途不同；交易服务的 ACCOUNT_INTERNAL_TOKEN 和 RISK_INTERNAL_TOKEN 必须与被调用服务一致。真实口令只放本机环境，不纳入 Git。

## 初始化与启动

1. 创建独立实验数据库环境。首次运行 Compose 可在 deploy 目录执行 docker compose -f docker-compose.dev.yml up -d mysql；先确认 mysql 的健康状态。Compose 仅在数据卷首次初始化时导入挂载 SQL；已有卷不会因文件修改自动更新。
2. 检查 deploy/sql/schema.sql 与 init-data.sql 后再初始化。schema.sql 含 DROP TABLE，init-data.sql 含 DELETE；两者都会破坏现有实验数据，不可把它们当作无损迁移。已有数据先备份，既有用户密码变更应做定向更新，不重跑整份初始化。
3. 配置实验 MySQL 账号及权限。至少覆盖用户凭据查询、账户/记账写入、交易/跨行转账单与渠道记录写入、风控规则及事件访问。现有示例权限不是完整生产权限清单，需用存款和跨行场景核验，不能仅以服务启动判断权限齐全。
4. 在 backend 目录以 JDK 21 执行 mvn install -DskipTests，构建前先停止占用同名 target JAR 的旧进程。随后分别在 user-service、account-service、risk-service、transaction-service、gateway 目录运行 mvn spring-boot:run。推荐依次启动用户、账户、风控、交易、网关。
5. 用户服务 mysql 模式的演示 identityId 为 UID-000001、UID-000002、OPS-ADMIN。前两者夹具密码 demo123，后者 admin123，仅为实验数据。登录字段是 identityId，不是 zhangsan/lisi/admin。本轮已将夹具改为 BCrypt；仅完成夹具兼容性测试，真实导入后需再次登录验证。
6. 在 frontend 目录执行 npm ci 与 npm run dev。默认 5173 端口通过 /api 代理到 8085。如网关改端口，设置 GATEWAY_URL 后重新启动 Vite。
7. 依次检查各服务 /actuator/health，通过网关登录，查询账户，再执行小额存款、查询状态及余额流水。用户、交易、账户、风控的 /api/v1/*/health 也可用于相应健康检查。健康接口通过不能替代资金链路验证。

## 日志与验收

应用日志默认输出到各服务终端；可通过 logging.file.name 配置本机日志文件。优先以 X-Trace-Id、requestId 和 tradeNo 关联调用。原始日志不直接提交，交付前清除个人信息、密码、服务令牌与会话令牌。验收必须核对账面余额、预留与可用余额关系，以及一笔交易只产生一次有效记账。

## 备份恢复与回滚

备份：停止新交易或进入受控维护窗口，使用 MySQL 8 对应的 mysqldump，以交互方式输入密码，启用 --single-transaction --routines --triggers 备份 payment_db。PowerShell 可使用 --result-file 指定备份路径，避免 shell 重定向改变编码。记录备份时间、代码版本、数据库版本与校验值，备份不纳入 Git。

恢复：在新建的隔离数据库实例验证备份可导入，运行 verify.sql 前先检查其重置语句，并核对关键行数、余额不变式、未决交易及请求号。确认恢复完整后再切换应用连接；不以文件存在代替恢复成功。

应用回滚：记录当前与上一可用提交，保留上一版 JAR 和配置快照；暂停新请求、停止新版进程，以旧版代码和兼容的数据库版本重启并做登录、查账户、存款冒烟。若表结构不兼容，先按已验证的数据库恢复流程处理。当前会话为进程内存，重启后需要重新登录，不能承诺会话跨实例共享。

本轮未执行 MySQL 备份恢复、应用版本回滚或完整资金冒烟，完成后由 S4 补充命令输出、时间和执行人。
