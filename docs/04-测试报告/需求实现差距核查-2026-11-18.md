# 当前缺少的接口与成员分工

更新日期：2026-11-18。基于 `80b44f6`，已在 `feat/s1-user-management` 补齐 S1 接口。

## 一、目前缺少什么接口

| 负责人 | 缺少的接口 | 用途 |
|---|---|---|
| S3 | 运营待处理交易列表接口 | 查询授权范围内需要人工处理的交易 |
| S3 | 人工核对交易接口 | 运营填写原因，沿原交易核对渠道结果并留痕 |
| S3 | 资金恢复重试接口 | 运营对有明确失败依据的交易重试恢复，保证幂等并留痕 |
| S3 | 风险记录查询接口 | 查询授权范围内的规则命中、拒绝原因和关联交易 |

以下接口按优先级安排，不必和上面的主要缺口一起做：

- **S3：回单下载接口** `GET /api/v1/transactions/{tradeNo}/receipt`，实验一列为 P2。
- **S3：风险告警处置接口**，实验一列为 P2。
- **S3：风控规则、风险名单的维护和审批接口**，先由小组确认本轮是否实现。

除已有契约中列明的路径外，其余新接口路径由对应负责人统一约定。

## 二、每个人应该干什么

| 成员 | 当前要做的事 |
|---|---|
| **S1：用户与认证** | 注册与模拟实名、本人资料、运营客户列表、管理员授权接口已完成；接下来配合 S4 配置数据库与管理员账号，配合 S5 对接页面。 |
| **S2：账户与记账** | 账户接口基本齐全。补“新日限额不得低于当天已成功＋已占用金额”的校验；与 S3 明确风控解除依据如何记录和核验。 |
| **S3：交易与风控** | 补上表中的运营与风控接口；现有交易查询接入运营账户范围和查询原因审计。自动恢复任务不能代替人工核对、恢复重试接口。 |
| **S4：数据库与部署** | 配合新增功能准备必要表结构、测试账号和授权数据；统一各服务启动配置，配合真实 MySQL 联调。 |
| **S5：前端** | 对接注册、资料维护、账户注销、个人限额、操作记录、运营冻结/解冻、人工核对和恢复页面；修复收款记录只取每个账户前 100 条的问题。 |

S2 的冻结、解冻、注销、个人限额、操作记录接口已有实现，S5 应直接对接，不需要重复开发接口。

## 三、需要先说清楚的两件事

1. **取款流程：S1、S3 一起确认。** 实验一要求模拟渠道的成功、失败、未知结果，目前取款直接执行本地记账。需要补渠道处理，或者正式确认需求变更。
2. **交易查询：S1、S3 一起确认。** 实验一要求查询只返回状态，目前查询可能触发渠道核对并推进记账。需要统一口径。

- 账户回归和存款链路已有真实 MySQL 测试记录；其他业务及浏览器场景仍需分别联调。
