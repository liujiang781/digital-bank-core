## 2. 发给 S1（复核认证与网关、调用身份）

1. **身份来源**：S3 的对外接口通过 `request.getUserPrincipal()` 取身份（`TransactionAccess`），不信任客户端身份头。请 S1 复核"伪造身份头"用例对 `POST /api/v1/deposits`、`GET /api/v1/transactions/{tradeNo}` 是否被过滤器拦截。
2. **越权行为**：S3 已验证非本人查询返回 404 `TRADE_NOT_FOUND`（不暴露他人交易号是否存在），真实联调中 `UID-000002` 查 `UID-000001` 的交易得到 404。请 S1 在真实网关再回归一次。
3. **新错误码路径**：存款非 CNY 现在返回 400 `INVALID_ARGUMENT`（之前被当 CNY 受理），请 S1 回归"登录后存款非法币种"是否被网关正确透传 400。
4. S3 对外接口清单（本轮覆盖）：`POST /api/v1/deposits`、`GET /api/v1/transactions/{tradeNo}`、`GET /api/v1/transactions`。

## 3. 发给 S2（复核记账与数据库断言）

1. **币种口径不变**：S3 存款侧始终以 `CNY` 编排，`currency` 非法值现在在 S3 侧提前 400 拒绝，不会再传入 S2。S2 无需改代码。
2. **需 S2 复核的记账语义**（S3 侧已保证，请 S2 在真实库复核资金效果）：
   - 成功存款只上报一次受理与一次成功回执，`channel_request_id=CHD+tradeNo` 唯一；
   - 同键同内容重放返回原 `tradeNo`，不再次调用 S2 受理；
   - 同键异内容 S3 返回 409 `REQUEST_CONFLICT`，原单要素不变；
   - 风控拒绝时 S3 调用 `POST /internal/v1/postings/failures`，不调用 `deposit-acceptances`，不产生渠道记录——请 S2 复核此时无资金流水；
   - `UNKNOWN` 回执保持待确认，S3 不把它上报为 SUCCESS，也不把它当作 FAILED。
3. **S2 需要的样例数据**（真实联调已产出，可复核）：`accountId=ACC_S2_001`，成功单 `tradeNo=TRD202611179836A6F9`、`TRD20261117F1EA18F7`，失败单 `TRD202611174B6065C4`，风控拒绝单 `TRD20261117DA6BC24E`；`mock_channel_deposit` 中对应 `result/evidence_id/reason_code/reconcile_attempts` 见《S3-实验四真实MySQL联调记录.md》第 3 节。

## 4. 发给 S4（数据库与环境）

1. **环境变量**（S3 两个服务启动必须，请 S4 在 `.env` / 启动脚本确认）：
   - `TRANSACTION_DB_URL / TRANSACTION_DB_USER / TRANSACTION_DB_PASSWORD`
   - `RISK_DB_URL / RISK_DB_USER / RISK_DB_PASSWORD`
   - `ACCOUNT_INTERNAL_TOKEN`（S2/S3 同值，≥32 字节随机）
   - `RISK_INTERNAL_TOKEN`（transaction-service 与 risk-service 同值）
   - `TRANSACTION_INTERNAL_TOKEN`（保护 S3 模拟渠道演示接口）
   - `MOCK_CHANNEL_RESULT=SUCCESS`（默认，联调结束恢复）
2. **表与数据**：`mock_channel_deposit` 已在 schema 中；`risk_rule` 需预置 `RK-01 ACCOUNT_STATUS`、`RK-02 LIMIT_POLICY(50000/10000/50000)`，演示数据见 `init-data.sql`。
3. **限额值口径**：S3 测试按 存款单笔 50000.00 / 出账单笔 10000.00 / 出账日累计 50000.00 执行，请 S4 确认联调库 `risk_rule` 与之一致。
4. **端口提醒**：S4 的 `start-all.ps1` 通过单个 `SERVER_PORT` 覆盖所有服务端口，直接跑会全部挤到一个端口（本机实测 user/account/transaction/risk 全试图绑定 18080 导致只起来一个）。建议启动脚本按服务分别设置端口，或业务服务不设 `SERVER_PORT`、仅网关设。这是 S4 的脚本问题，请 S4 修正。
5. S3 侧本轮无新增数据库账号、无新增 DDL，部署拓扑不变。

## 5. 发给 S5（端到端联调与证据）

1. **S3 已产出真实 MySQL E2E 记录**：`docs/04-测试报告/S3-实验四真实MySQL联调记录.md`（登录→查账户→存款→重放→冲突→渠道 FAILED/UNKNOWN/收敛→风控拒绝→非法币种→越权，含库前后值）。S5 可参考或在其基础上补截图。
2. **S3 提供的存款请求样例**（令牌隐去，`requestId` 用 `[guid]::NewGuid().ToString()`）：

   ```json
   {
     "accountId": "ACC_S2_001",
     "amount": "100.00",
     "currency": "CNY",
     "purpose": "实验四存款联调",
     "requestId": "fa84bd50-4250-4295-a3f7-e6034f88ff37"
   }
   ```

   经网关 `POST http://127.0.0.1:8080/api/v1/deposits`（本机 8080 被占用时为 18080），`Authorization: Bearer <登录令牌>`。

3. **渠道三态切换**（S3 内部接口，`X-Internal-Token: <TRANSACTION_INTERNAL_TOKEN>`，直连交易服务 8083）：

   ```bash
   curl -X POST http://127.0.0.1:8083/internal/v1/channel/mode \
     -H "Content-Type: application/json" \
     -H "X-Internal-Token: <TRANSACTION_INTERNAL_TOKEN>" \
     -d "{\"result\":\"UNKNOWN\"}"
   ```

   `result` 可选 `SUCCESS` / `FAILED` / `UNKNOWN`；查询渠道记录 `GET /internal/v1/channel/deposits/{tradeNo}`（同 header）。先 `UNKNOWN` 再切 `SUCCESS` 后用原用户 `GET /api/v1/transactions/{tradeNo}` 触发核对，`data.status` 未变前不要当成功。

4. **需要 S5 回填**：S5 自己的操作截图、`tradeNo/requestId/traceId` 与余额/流水前后值，交 S4 和 S2/S3 复核。
