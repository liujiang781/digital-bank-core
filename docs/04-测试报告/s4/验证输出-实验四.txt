19.3 本轮发现（2 项，均为 S3 代码与表结构/业务键不一致）

DEF-S4-005  risk_list_entry 缺 approved_by 列（已修复）
 现象：名单审批与名单查询返回 500 INTERNAL_ERROR
 根因：RiskListService 的 SELECT/INSERT/UPDATE 均引用 approved_by，
       而 schema.sql 的 risk_list_entry 无此列
       （见 RiskListService.java 查询与 applyList 处）
 处置：ALTER TABLE risk_list_entry
         ADD COLUMN approved_by VARCHAR(64) DEFAULT NULL AFTER created_by;
       执行后 8/9 步转为 PASS。
 建议：由 S4 在 schema.sql 永久补该列（ListEntryView 本就有 approvedBy 字段）。

DEF-S4-006  名单 REMOVE 静默失效（未修复，需 S3 改）
 现象：REMOVE 提交并审批后接口返回 code=SUCCEEDED，
      但 GET /risk/lists 仍返回 total=1、enabled=true，条目未删除。
 证据：REMOVE 审批返回 version=0（库里查不到该 entry_id），
       查询列表仍有 RLE-BLACKLIST-ACCOUNT-C69F2F3D3CFE。
 根因：每次提交都生成新的 entryId，applyList 的 REMOVE 分支
       执行 DELETE ... WHERE entry_id = ?，用新 entryId 删不到旧行，
       影响 0 行；但 risk_change_request 仍被置为 APPLIED。
 影响：名单无法通过审批流移除，黑名单会永久残留（ACC_S2_002 已被拦截）。
 建议：REMOVE 改为按业务唯一键定位
       WHERE list_type=? AND subject_type=? AND subject_id=?，
       并校验影响行数，为 0 时抛冲突而不是静默成功。

DEF-S4-007（推断，未实测）  同一主体重复 UPSERT 会撞唯一键
 依据：risk_list_entry 有 UNIQUE KEY uk_list_subject(list_type,subject_type,subject_id)，
       而 applyList 用 version==null 判断走 INSERT；由于 entryId 每次新生成，
       已存在的条目必然查不到，重复 UPSERT 将撞 uk_list_subject（1062）。
 说明：本轮 UPSERT 能成功是因为此前该主体无条目；建议 S3 复现确认，
       修法与 DEF-S4-006 相同（先按业务键查存在性）。
