## 1. 目标

| 编号 | 目标 | 对应交付 |
| --- | --- | --- |
| P1 | 验证 5 个服务在 22 表结构上可正常读写 | 5/5 health UP |
| P2 | 量化登录、余额查询、流水查询、存款写入四类路径的响应时间 | 四个场景的 min/avg/p50/p95/p99/max |
| P3 | 验证存款幂等与余额一致性 | 重放同 `requestId` 返回同一 `tradeNo` |
| P4 | 压测数据可完整回收 | `sql/02-perf-cleanup.sql` 实测 |

非目标：并发容量规划、连接池调优、长时间稳定性、数据库基准测试。本次为**单机串行**趋势测试，不作为性能基准结论。

## 2. 测试拓扑

```
PowerShell perf-test.ps1
        │ HTTP
        ▼
 gateway :8085
   ├─ user-service        :8081  → MySQL s2_exp4_test
   ├─ account-service     :8082  → MySQL s2_exp4_test
   ├─ transaction-service :8083  → MySQL s2_exp4_test
   └─ risk-service        :8084  → MySQL s2_exp4_test
```

- 主机：Windows 10/11 单机，MySQL 8.0.46 本机实例
- 客户端与网关同机，网络 RTT ≈ 0
- 每次请求串行发出（前一次结束后再发下一次），测量端到端耗时
- 数据源为 `DriverManagerDataSource`（无连接池），因此写路径含真实建连成本

## 3. 场景设计

| 场景 | 方法与路径 | 样本量 | 关键参数 | 判定 |
| --- | --- | --- | --- | --- |
| health | GET `/actuator/health` ×5 端口 | 5 | — | 5/5 返回 `UP` |
| login | POST `/api/v1/auth/login` | 10 | `UID-000001` / `demo123` | HTTP 200 且返回 token |
| balance | GET `/api/v1/accounts/{id}/balance?reason=` | 200 | `ACC_S2_001` | HTTP 200 且返回 `bookBalance` |
| transaction_list | GET `/api/v1/transactions?reason=&page=1&pageSize=20` | 200 | 同上 | HTTP 200 且返回 `total` |
| deposit | POST `/api/v1/deposits` | 20 | 每笔 `1.00`，独立 UUID | 全部 `SUCCESS` |

存款细节：
- body：`{"accountId":"ACC_S2_001","amount":"1.00","requestId":"<uuid>"}`
- 请求头 `X-Request-Id` 必须与 body 内 `requestId` 完全一致，否则被拒
- 每笔使用新 UUID，避免命中幂等键

## 4. 脚本与参数

```powershell
powershell -ExecutionPolicy Bypass -File scripts\perf-test.ps1 `
  -BaseUrl http://localhost:8085 `
  -Identity UID-000001 -Password demo123 `
  -AccountId ACC_S2_001 `
  -LoginCount 10 -ReadCount 200 -WriteCount 20 -DepositAmount 1.00
```

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| `BaseUrl` | `http://localhost:8085` | 网关地址 |
| `Identity` / `Password` | `UID-000001` / `demo123` | 存款必须是账户本人（对象级授权） |
| `AccountId` | `ACC_S2_001` | 演示账户 |
| `LoginCount` | 10 | 登录样本 |
| `ReadCount` | 200 | 余额、流水各 200 次 |
| `WriteCount` | 20 | 存款笔数 |
| `DepositAmount` | `1.00` | 单笔金额，需与清理脚本一致 |

输出：
- `evidence/perf-<stamp>.csv`：逐请求明细（场景、序号、HTTP、毫秒、结果）
- `evidence/perf-<stamp>.txt`：按场景汇总的 min/avg/p50/p95/p99/max

## 6. 数据分析

1. **login ≈ 309 ms**：明显高于其他读路径，主因是 BCrypt cost=12 的密码校验（CPU 密集），与数据库无关。安全强度与登录延迟是权衡关系，当前值对演示系统可接受。
2. **balance p95 ≈ 74 ms**：链路为 网关 → account-service → `account` 单行主键查询 → 返回。主要成本是 HTTP 转发与 JSON 序列化；无连接池时每次新建 MySQL 连接。
3. **transaction_list p95 ≈ 61 ms**：走 `idx_transaction_account_created`（account_id + created_at）分页，20 条/页，随页大小线性增长。
4. **deposit p95 ≈ 165 ms**：写路径包含幂等键写入、账户乐观锁更新、流水落库、渠道记录、审计日志，且单事务提交，成本约为读路径的 2-3 倍，符合预期。
5. **离散度**：p99 与 max 接近，无长尾毛刺，说明 22 表结构上的索引与约束未引入额外抖动。

## 7. 压测数据回收

压测写入的 20 笔 `1.00` 存款在实测后由 `sql/02-perf-cleanup.sql` 回收，实测结果：

| 项 | 值 |
| --- | --- |
| 命中待删交易 | 21 笔（20 笔压测 + 1 笔功能验收） |
| 回退金额 | 21.00 |
| 清理前余额 | 50021.00 |
| 清理后余额 | 50000.00 |
| 清理后残留 | 0 |
| 删除范围 | `mock_channel_deposit` → `transaction_flow` → `transaction`，`audit_log` 保留 |

脚本先输出预览（将删除的 `trade_no` 列表与合计金额），再在事务内删除并回退余额，最后输出清理后余额与残留数。若窗口内存在真实同额存款，需先把 `@since` 收窄到压测开始时间。

## 8. 局限与后续

| 局限 | 影响 | 建议 |
| --- | --- | --- |
| 串行请求、单客户端 | 只能看单请求延迟，无法得出并发吞吐/TPS 上限 | 用 JMeter/wrk 增加并发梯度（10/50/100） |
| 无连接池 | 每次请求新建 MySQL 连接，写路径偏慢 | 换 HikariCP 后复测对比 |
| 未开慢查询日志 | 无法定位具体 SQL 耗时 | 开 `slow_query_log`，阈值 50ms |
| 未覆盖转账、风控、审批路径 | 仅覆盖存/查 | 补充 `transfer_order`、`risk_event` 压测 |
| 单机同机部署 | 网络成本为 0，绝对值偏乐观 | 跨机部署后复测 |
| 未做 24h 稳定性 | 无法发现连接/内存泄漏 | 加入持续压测与监控 |
