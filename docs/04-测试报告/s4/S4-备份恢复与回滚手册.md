# S4 备份、恢复与回滚手册

> 实测时间：2026-11-24 17:15:25
> 实测库：`payment_db`（已重建为 22 表 / 17 外键 / 48 CHECK，含 21 笔真实交易）
> 证据：`evidence/drill-20261124-171525.log`、`evidence/drill-20261124-171525/`（全量 dump、表级 dump、逐步 CSV）
> 结论：**14 个步骤全部 PASS，总耗时 4.11 秒，恢复后结构断言 22/17/48 一致，数据 21 笔交易、余额 50021.00 完整**

## 1. 术语

| 术语 | 定义 | 本手册对应 |
| --- | --- | --- |
| 备份 | 可独立用于重建数据库的一致性副本 | `full.sql`（逻辑全量）、`t_*.sql`（表级） |
| 恢复（restore） | 用备份把数据/结构还原 | 3b、4b、5b、6b |
| 回滚（rollback） | 撤掉本次变更，回到变更前状态 | 6a：DROP 新表 `risk_freeze_release`，22→21 |
| 前滚（roll forward） | 用备份重新应用变更，回到目标状态 | 6b：从表级 dump 恢复，21→22 |
| RTO | 从故障到业务恢复的时间 | 各步 `seconds` 字段 |
| RPO | 可容忍丢失的数据时间窗 | 逻辑备份 = 上次 dump 时刻；本次未做 binlog PITR |

## 2. 备份策略

### 2.1 全量逻辑备份

```powershell
mysqldump -u <user> -p --single-transaction --no-tablespaces `
  --routines --triggers --default-character-set=utf8mb4 `
  --result-file=D:\backup\full.sql payment_db
```

- `--single-transaction`：InnoDB 一致性快照，不锁表
- `--no-tablespaces`：无 PROCESS 权限的账号也能导出
- `--routines --triggers`：保留存储过程与触发器
- 先在临时 ASCII 目录生成，再复制到交付目录，避免中文路径在 `source` 时被解析破坏

### 2.2 表级备份（用于快速单表恢复）

```powershell
mysqldump -u <user> -p --single-transaction --no-tablespaces `
  --default-character-set=utf8mb4 --result-file=D:\backup\t_account.sql payment_db account
```

用于三类高频事故：误 DROP 单表、单表数据被污染、结构变更需要单表回退。

### 2.3 建议的保留策略

| 层级 | 频率 | 保留 | 用途 |
| --- | --- | --- | --- |
| 全量 dump | 每日 02:00 | 7 天 | 库级灾难恢复 |
| 变更前快照 | 每次上线前 | 至下次上线 | 版本回滚 |
| 表级 dump | 大批量数据变更前 | 30 天 | 单表恢复 |
| binlog | 持续 | 7 天 | 时间点恢复（PITR），本次未实测 |

## 3. 演练前置条件

1. 数据库已按 `schema.sql` 建好 22 表，并已灌入 `init-data.sql`
2. 执行账号具备：`SELECT / INSERT / UPDATE / DELETE / CREATE / DROP / LOCK TABLES`（本次用隔离库专用账号，避免动到 `payment_db`）
3. 服务可停：演练包含 DROP DATABASE，必须先停业务进程，否则连接占用会让 DDL 等待元数据锁
4. 磁盘可用空间 ≥ 2 倍当前库大小

## 4. 演练步骤与判定

| 阶段 | 动作 | 判定标准 | 实测 |
| --- | --- | --- | --- |
| 1 | 基线快照：表数、客户数、账户数、交易数、余额 | 与预期一致 | PASS 0.38s（22 表 / 4 客户 / 2 账户 / 21 交易 / 50021.00） |
| 2a | 全量逻辑备份 | dump 大小 > 10KB 且含 22 个 `CREATE TABLE` | PASS 0.24s（67.5KB / 22 表） |
| 2b | 表级备份 `account`、`risk_list_entry`、`risk_freeze_release` | 3 个文件均生成 | PASS 0.23s |
| 3a | **故障 A**：`DROP TABLE risk_list_entry` | 表数 22→21 | PASS 0.15s |
| 3b | 表级恢复 `risk_list_entry` | 表数回到 22 | PASS 0.22s |
| 4a | **故障 B**：把 `ACC_S2_001.book_balance` 改成 0.01 | 余额被污染 | PASS 0.12s |
| 4b | 表级恢复 `account` | 余额回到 50021.00，2 行数据 | PASS 0.30s |
| 5a | **故障 C**：`DROP DATABASE` | 库不存在 | PASS 0.55s |
| 5b | 重建库 + 导入全量 dump | 22 表重建成功 | PASS 1.10s |
| 5c | 恢复后数据核对 | 账户 2 / 客户 4 / 交易 21 / 余额 50021.00 | PASS 0.24s |
| 6a | **回滚演练**：DROP `risk_freeze_release`（22→21） | 表数 21，其余结构不受影响 | PASS 0.15s |
| 6b | **前滚恢复**：从表级 dump 恢复新表 | 表数回到 22 | PASS 0.17s |
| 7 | 最终结构断言 | `tables=22 fk=17 check=48` | PASS 0.26s |

总耗时 **4.11 秒**（本机、空载、数据量 21 笔）。

## 5. 关键结论

1. **单表故障恢复最快**：表级 dump 恢复到可用约 0.2 秒（RTO），适合误删单表、单表污染。
2. **库级故障 2 秒内可恢复**：DROP DATABASE 后重建 + 全量导入共 1.6 秒（空库 60.7KB）。数据量增长后 RTO 随 dump 大小线性上升，需按实际数据量重测。
3. **22 表相对 21 表的增量表可独立回滚/前滚**：`risk_freeze_release` 只有 1 个外键指向 `account_status_log`，不反向被引用，因此可以单独 DROP 再恢复，不影响其余 21 表。这是本次"完整回滚"演练的核心。
4. **回滚边界**：本次回滚只覆盖"新增表/新增列"这类结构变更。若变更涉及数据迁移（如列拆分、口径变更），回滚必须依赖变更前全量 dump，不能只靠结构 DDL 反向执行。
5. **RPO**：逻辑备份的 RPO = 距上次 dump 的时间。本次未启用 binlog 时间点恢复，若需秒级 RPO，必须开启 `log_bin` 并用 mysqlbinlog 重放。

## 6. 操作手册（可直接执行）

### 6.1 演练（自动，7 阶段）

```powershell
# 默认库 payment_db，交互式输入口令
powershell -ExecutionPolicy Bypass -File scripts\drill-backup-rollback.ps1

# 指定库与账号（非交互，用于隔离库）
powershell -ExecutionPolicy Bypass -File scripts\drill-backup-rollback.ps1 `
  -Database payment_db -DbUser root -DbPassword ****** `
  -OutDir ..\evidence
```

产物：`evidence/drill-<stamp>.log` + `evidence/drill-<stamp>/`（`full.sql`、`t_*.sql`、`drill-steps.csv`）。

### 6.2 生产事故处理顺序

1. **先止损**：停写入（停服务或只读模式），避免二次污染
2. **再定位**：确认是单表、单库还是实例级
3. **选择恢复粒度**：
   - 单表 → 表级 dump（RTO 最短）
   - 单库 → 全量 dump（恢复到最近备份点）
   - 需要精确到秒 → binlog PITR（本手册未覆盖）
4. **恢复后核对**：表数/FK/CHECK、关键业务表行数、核心账户余额
5. **记录**：把本次 RTO、丢失数据量、根因写入事故记录

## 7. 未覆盖项（如实说明）

| 未覆盖 | 原因 | 风险 |
| --- | --- | --- |
| binlog 时间点恢复（PITR） | 未开启 `log_bin` | 只能恢复到上次 dump，RPO 较大 |
| 物理备份（XtraBackup/克隆） | 环境未安装 | 大库恢复慢 |
| 主从切换 | 单实例部署 | 无高可用 |
| 大容量数据恢复 | 仅 21 笔交易 | RTO 随数据量增长，需按真实规模重测 |
| 跨版本恢复 | 仅 8.0.46 → 8.0.46 | 降版本恢复不保证兼容 |
