## 5. 执行说明与注意事项

1. **`information_schema` 会被权限过滤**：用 `account_service` 查询表数时只返回已授权的 11 张表，而非全库 16 张。表数、外键数、CHECK 数必须用 root 或对全库有 SELECT 的账号执行；`deploy/scripts/verify-db.ps1` 就是为此设计（运行时交互输入 root 口令，不落盘）。
2. **验证脚本遇错误继续**：`verify.sql` 中有 3 处预期错误——两处故意制造 `Duplicate entry`，一处故意插入 `amount = -50.00` 触发 `chk_transaction_amount`（8.0.16+ 才生效）。必须用 `mysql -f` 执行，否则后续清理语句不执行，残留 `VERIFY-%` 数据。
3. **演示口令**：`init-data.sql` 内置与 S2/S3 文档一致的演示口令（zhangsan/lisi = `demo123`、admin = `admin123`），库中只存 BCrypt 哈希；需改口令时执行 `set-demo-password.sh`。真实数据库与服务账号口令只在 `.env.local`，不入库。
4. **数据重置**：重跑 `init-data.sql` 即可回到基线（余额 50000 / 30000），无需重建库；只有改了表结构才需要重跑 `schema.sql`（会 DROP 表，先备份）。
5. **余额探测值**：若上一次 `verify.sql` 被中断（PowerShell 5.1 会把 mysql 的 stderr 当作错误并中止管道），`ACC_S2_001` 可能停在 50100.00。`verify.sql` 开头重置为 50000.00、结尾再复位一次，因此以最后一次完整执行的输出为准（当前实测已复位为 50000.00 / 30000.00，`VERIFY-%` 残留为 0）。root 级证据文件：`verify-output-<时间戳>.txt`。

## 附：DEF-S4-004 登录阻塞（2026-11-19）

合并 `main@75ddc06`（PR #41，S1 注册资料与角色授权）后，`POST /api/v1/auth/login` 经网关 8085 与直连 8081 均返回 503 `{"code":"SERVICE_UNAVAILABLE","message":"授权存储暂时不可用"}`。

失败点为 `staff_authorization` 的 `SELECT role_id, version ... FOR UPDATE`。已排除：表结构（identity_id/role_id/version/updated_at 齐全）、账号匹配（仅 `bank_user@'%'`）、认证插件（`mysql_native_password`）、连接库（`payment_db`）、MySQL 错误日志（无认证失败记录）。

**根因（已实测确认）**：MySQL 8.0.13 的锁读权限检查存在缺陷——即使 `bank_user` 已获得 `staff_authorization` 的表级 `SELECT, INSERT, UPDATE, DELETE`，执行 `SELECT ... FOR UPDATE` 仍返回 **ERROR 1143（`ER_COLUMNACCESS_DENIED_ERROR`）**，被判定为列级越权。对照组：`credential`、`user_command`、`customer`、`staff_authorization` 上的 `FOR UPDATE` 全部失败；`account`（仅表级 SELECT）报 1142；不带 `FOR UPDATE` 的普通 SELECT 全部正常。这解释了为何 `performance_schema` 中「无错误码」——早期采样窗口内服务并未运行，样本无效。

**处置**：`deploy/sql/exp4-grant.sh` 先补齐表级授权，再临时追加 8.0.13 兼容的列级授权（`GRANT SELECT (identity_id, role_id, version), UPDATE (...) ON staff_authorization` 等两条）绕过该缺陷，登录恢复。

**后续（2026-11-19）**：本机 MySQL 升级到 **8.0.46** 后，列级授权已撤销，`SHOW GRANTS` 仅剩 7 条表级授权，`SELECT ... FOR UPDATE` 复测正常（不再报 1143）。因此脚本已删除那两条列级授权，恢复纯表级最小授权；CHECK 约束也随重跑 `schema.sql` 生效（见 DEF-S4-001）。

**复测结果**（2026-11-19，`main@75ddc06` 合并后）：

```

code=SUCCEEDED identity= role= scope= tokenLen=43
--- login via 8085 ---
code=SUCCEEDED identity= role= scope= tokenLen=43
```

**移交 S1 的改进建议**（不影响当前结论）：
1. `StaffAuthorizationService` 第 35–38 行 `catch (DataAccessException)` 应补 `log.error`，否则底层异常码被吞，排查只能靠抓包/探针。
2. `UserManagementRepository.readAuthorization` 用了 `SELECT ... FOR UPDATE`，但表上已有 `version` 字段。建议改为乐观锁（`UPDATE ... WHERE version = ?`），既避免锁读，也避开 8.0.13 的权限缺陷。

网关端口已按 S1 口径统一为 8085，健康检查 5/5 PASS（原始输出 `verify-output-8085.txt`）。
