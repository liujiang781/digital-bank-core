## 2. 范围与方法

本轮分两层执行。

第一层是接口端到端。脚本经网关执行登录、账户查询、存款、取款、本行转账、跨行转账、交易查询、余额与流水、幂等重放、限额边界、渠道三态和越权查询。脚本名是 `s5_e2e.py`。渠道切换直连交易服务的内部演示接口，因为网关不路由该路径。

第二层是页面测试。脚本用 Edge 无头浏览器执行登录、错误提示、未登录跳转、存款二次确认、金额校验和连续点击。脚本名是 `s5_page_test.py`。

## 7. 问题与待复核项

1. **收敛不是即时的。** 渠道切回 SUCCESS 后，第一次查询仍返回 UNKNOWN。脚本轮询 8 次、21.4 秒后看到 SUCCESS。演示时要提前说明这个延迟。
2. **大额取款先命中限额。** 999999.00 返回 SINGLE_LIMIT_EXCEEDED，不是余额不足。低余额等价类改用专门开立的账户完成。
3. **页面连续点击残留确认弹窗，已修复。** UI-S5-006 首轮发现连点两次会出现两个确认框。修复方式是给存款页加确认锁，并让按钮在确认期间进入 loading 态。修复后重跑 6 条页面用例，全部通过。
4. **测试脚本修订过四次。** 早期轮次出现过 URL 中文未编码、误点“退出登录”、未点二次确认三类脚本问题。修订后的最终轮次全部通过。过程文件保留在证据目录，文件名带“首轮”“复跑”等后缀。
5. **前端 README 与配置不一致。** README 写代理指向 8080，`vite.config.js` 实际指向 8090。本文只报告，不修改文档。
6. **状态口径以运行代码为准。** 实际接口返回账户状态 ACTIVE，交易状态 SUCCESS/FAILED/UNKNOWN。脚本按实际返回值判定。
7. **数据复位脚本的账户编号不匹配，已修改。** `restore-demo.sql` 原来只复位 `ACC_S2_001/002`。现在两套编号一起复位，余额仍是 50000.00 和 30000.00。已在临时库验证四个账户都复位成功。本次没有在真实库执行该脚本，避免清掉其他成员的证据。
